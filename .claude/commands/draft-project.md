tomixy's biography（このリポジトリ）のproject記事として、本文の草案をMDXで書いてください。

## 今回のプロジェクト

対象：$ARGUMENTS

既存の`src/content/project/<slug>.mdx`が指定された場合は、そのfrontmatterを読み、本文だけを書きます（frontmatterは勝手に書き換えず、変更提案は最後の報告に回す）。

対象が空、または以下の条件が分からない場合は、**書き始める前に**まとめて質問して確定させてください。

- どんなものを作ったか（1〜2行）
- 作った動機・解決したかった課題
- 紹介したい見どころ（機能・設計・工夫）を3〜6個
- 公開URL / GitHub / npm / PDFの有無
- 関連するtech記事やblog記事があるか（詳細をそちらへ委ねられる）
- 制作中か、完成しているか
- 分量：短め（リード段落だけ、300〜600字）／標準（見どころ3〜4本、1,500〜2,500字）／充実（見どころ6本以上、5,000字以上）
- スクリーンショットや図版が`src/assets/projects/<slug>/`にあるか

## 先に読むもの

- 手本にする既存記事を2〜3本
  - 機能紹介が中心の充実版：`src/content/project/color-prism.mdx`, `src/content/project/pocket-excel-learning.mdx`
  - ライブラリ・ツール：`src/content/project/astro-mdx-directive.mdx`, `src/content/project/wgsim-rs.mdx`
  - 短い紹介＋tech記事への委譲：`src/content/project/summario.mdx`
- `src/layouts/project.astro`（ページ上で本文の外側に何が表示されるか）
- `src/content/tag.yaml`（使えるタグの確認）
- `CLAUDE.md`

`tomixyz-biography-v2.mdx`と`imaging-math.mdx`は手本にしないでください（見出しだけ置かれた執筆途中の記事です）。

手本記事から借りるのは**構成の骨格と記法だけ**。言い回しや文の並びを流用して「名詞を差し替えただけの記事」にしないでください。

## 本文の外側にあるものを繰り返さない

`src/layouts/project.astro`が、本文の前に次を表示します。本文で改めて紹介しないでください。

- タグ一覧、タイトル、`description`（キャッチコピーとして表示される）
- サイト・GitHub・npm・PDFへのリンクボタン
- カバー画像（`image`）と日付

本文は「ヘッダーを見た人がその先に読みたいこと」から始めます。技術スタックの列挙もタグが担うので、本文では**なぜその技術を選んだか**を書くときだけ触れます。

## 構成のルール

- H1は書かない（frontmatterのtitleがH1）。見出しは`##`と`###`だけ
- 冒頭は見出しなしのリード1〜3段落。**何を作ったか**と**なぜ作ったか**（困っていたこと、きっかけ）。制作中なら「〜を制作しています」、完成しているなら「〜を制作しました」
- `##`は見どころ1つにつき1本。機能・設計・工夫のうち、そのプロジェクトらしさが出るものだけを選ぶ
- project記事の見出しはtech記事より短く、名詞句や体言止めでよい（「強化されたタグ機能」「図版はすべてTikZで」「Tailwind CSSを剥がす」「セル操作、数式の編集や実行に対応したデモ」）
- 各`##`セクションの基本形：何ができるか → なぜそうしたか → 実際のページ・デモへのリンク → スクリーンショット
- 該当ページへのリンクは`- [「色の理論」ページ](https://...)`のように箇条書きの1行で置く。同一サイト内なら`/tech/<slug>`のようなルート相対で書く
- `###`は、1つの`##`の中で機能を並べるときだけ使う
- 実装の詳細を掘る話は、この記事では深追いせず、tech記事へ委ねて`- [記事タイトル](/tech/<slug>)`でリンクする。該当記事がまだ無ければ、書くべきtech記事の候補として最後に報告する
- 「まとめ」「おわりに」という見出しは作らない。最後のセクションの流れのまま終わる。制作中のプロジェクトなら、これから作りたいものに触れて終わってよい
- frontmatterだけで本文が無いprojectも既に多数ある。書くことがなければ無理に埋めず、リード段落だけで終わらせる判断をしてよい

## 文体のルール

- 敬体（〜です／〜ます）を基本にする。project記事は初見の読者への紹介文なので、tech記事の制作記録より少し丁寧に書く
- 一人称は「私」。使いすぎない
- 機能の説明は断定する。設計の良し悪しや所感は「〜と感じています」「〜と思います」で留める
- 自分がなぜ困っていたか、なぜ作りたかったかは具体的に書く（「自身の学習でも、どうすれば丸暗記ではなく視覚的に理解できるかに悩み、このサイトを制作するに至りました」のような書き方がこのサイトの持ち味）
- 外部のライブラリ・サービス・規格には初出で公式サイトへのリンクを張る

## 避けること

- ヘッダーが既に見せている情報（タイトル、description、技術タグ、リンク）の言い換え
- 機能の羅列だけで、なぜそうしたかが無いセクション
- 「〜ではなく、〜」という対比構文の多用。平叙文で言えるなら平叙文にする
- 比喩・擬人化、宣伝文句めいた形容（「圧倒的な」「革新的な」など）
- 確認していない数値（図版の点数、ユーザー数、パフォーマンス改善率）の捏造。件数を書くなら実際に数える
- 本文中の絵文字

## 記法のルール

- frontmatter：`title` / `date: "YYYY-MM-DD"` / `image`（必須）/ `description`（必須）/ `tags` / `url` `github` `npm` `pdf`（任意）/ `editing` / `pinned`
- `description`はキャッチコピーとして表示される。句点をつけない短い句にする。例：「色彩からCG・画像処理までつながるビジュアル学習サイト」「wgpuとwinitのコードをシンプルに書くためのラッパー」
- **本文が未完成のうちは`editing: true`をつける**。projectコレクションには`draft`が無く、`editing: true`のときは本番ビルドで本文が非表示になる（`src/pages/projects/[slug].astro`）
- `image`は`src/assets/projects/<slug>/<file>`への相対パスで、ファイルが実在しないとビルドが失敗する。画像が1枚も無い場合はパスを捏造せず、必要な画像として最後に報告する
- `tags`は`src/content/tag.yaml`に存在するキーだけを書く。無いタグが必要なら本文には書かず、最後の報告で候補として挙げる
- 強調：初出の重要語は`==用語==`、要点の一文は`=p=文==`または`**文**`
- インラインコードには言語注記をつける：`` `import{:js}` `` `` `-fuzz{:bash}` ``
- コードブロックのメタ情報を活用する（例：` ```rs showLineNumbers {38,41} title="winitでウィンドウを作成するコード（抜粋）" `）。Before/Afterの比較には`title="Before：..."` / `title="After：..."`を使う
- 画像：`import img_Xxx from "../../assets/projects/<slug>/xxx.png"`をfrontmatter直後にまとめ、次のいずれかで表示する
  - `<FigureBox src={img_Xxx} caption="..." maxWidth="600px" />`（`$/components/image-wrapper/FigureBox.astro`）
  - 縦に並べる：`<VStack>`、横に並べる：`<GridGallery col={2}>`（`$/components/placement/`）
  - 画像の横に説明文を置く：`<ContentWithImage src={img_Xxx}>`（`$/components/image-wrapper/ContentWithImage.astro`。中にMarkdownを書くので前後に空行を入れる）
- デモへのリンク：`::DemoLink[ラベル]{url="..."}`、結果画像つきは`<DemoLinkWithResult url="..." title="..." result={img_Xxx} />`
- コンポーネントの直前に空行が必要な箇所でprettierに崩されるときは、`{/* prettier-ignore */}`を置く（既存記事の慣習）
- コードスタイルはprettier準拠（セミコロンなし、ダブルクォート、120字）

## 出力

- 既存ファイルがあればその本文を書き、無ければ`src/content/project/<slug>.mdx`を新規作成する（slugはリポジトリ名に合わせる）
- スクリーンショットが必要な箇所は文章で埋めず、`{/* TODO: 図版 */}`を置く
- 事実が確認できない箇所も書かずに`{/* TODO: 要確認 */}`を置く
- 書き終えたら、次を報告する：`description`案（2〜3案）／追加が必要なタグ／必要なスクリーンショットの一覧（どのセクションに何を撮るか）／別途書くべきtech記事の候補／判断に迷って私に決めてほしかった箇所

見どころが5本以上になりそうな場合は、いきなり本文を書かず、まず見出し案（`##`と`###`の一覧）を出して合意を取ってから本文に進んでください。
