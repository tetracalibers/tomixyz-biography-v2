## 観点ごとのセクションで書く

Summarioでは、1つのテーマ（用語や概念）につき1つのノートを作ります。そのノートは、==セクション==という単位で観点ごとに区切って書いていきます。全体の流れを組み立てるのではなく、まずは観点ごとの説明を揃えていくことで、理解を深めていく狙いがあります。

### 視点カードをドラッグして書き始める

サイドバーの「Blocks」タブには、「ひと言で表すなら？」「何を解決するために登場した？」「落とし穴となりそうなところは？」といった問いかけが書かれた==視点カード==が16枚並んでいます。

<FigureBox src={img_AllViewCards} caption="現時点で用意されている視点カード" />

穴埋め式のテンプレートにしなかったのは、用意された構成に書きたいことを当てはめる思考を持ち込みたくなかった、という理由があります。自分なら情報をどの角度から眺めるか？という方向性を、視点カードでサポートしつつ、自ら考えられるようにしたかったのです。

カードをエディタへドラッグ&ドロップすると、その観点を見出しに持つ空のセクションが、落とした位置に挿入されます。

  <source src="/movie/summario-dev/drag-view-card.webm" type="video/webm" />
</video>

書きかけの本文を壊さないことを優先し、ドロップ位置は細かく制御を行っています。ブロックとブロックの間に落とせばその位置へ、トップレベルの空段落の上に落とせばその段落と置き換わります。リストや引用の中、テキストの途中に落とした場合は、何も起こりません。

この制御は、ProseMirrorのプラグインとして`drop{:ts}`イベントを横取りする形で実装しています。Tiptapにはもともとブロックをドラッグして動かす仕組みがあるため、視点カードのドロップだけを見分けて、それ以外は本来の処理へ戻すよう実装しています。

```ts showLineNumbers {6-7,10-11} title="ドロップ位置を判定して挿入する"
drop: (view, event) => {
  // ドラッグ元のブロックタイトルがなければTipTapのデフォルトの挙動に任せる
  const title = getBlockTitle(event)
  if (!title) return false

  // ドロップ座標から近傍のposを取得（できなければデフォルトへ）
  const droppedPos = getDroppedPos(view, event)
  if (!droppedPos) return false

  const { pos, inside } = droppedPos
  const isInsideNode = inside > 0

  // ノードの「間」にドロップされた場合：その場所へ挿入
  if (!isInsideNode) {
    insertSectionAt(editor, pos, title)
    return true // TipTap のデフォルトのドロップ処理を停止
  }

  // トップレベル paragraph ならその位置へ挿入
  if (isTopLevelParagraphAt(view, pos)) {
    insertSectionAt(editor, pos, title)
    return true
  }

  // それ以外（テキスト途中や他ノード内）は何もしない
  return false
}
```

座標から文書内の位置を求めている`getDroppedPos(){:ts}`は、ProseMirrorの`posAtCoords(){:ts}`を呼ぶだけの関数です。

```ts title="ドロップ座標から文書内の位置を求める"
const getDroppedPos = (view: EditorView, e: DragEvent) => {
  const coords = { left: e.clientX, top: e.clientY }
  return view.posAtCoords(coords)
}
```

ドロップ位置判定の材料になっているのは、この`posAtCoords(){:ts}`が返す`inside{:ts}`です。これはドロップ座標がどのProseMirrorノードの内側にあたるかを示す値で、どのノードの内側でもなければ`-1{:ts}`になります。

```ts showLineNumbers{6} title="ドロップ位置を判定して挿入する（再掲）"
// ドロップ座標から近傍のposを取得（できなければデフォルトへ）
const droppedPos = getDroppedPos(view, event)
if (!droppedPos) return false

const { pos, inside } = droppedPos
const isInsideNode = inside > 0
```

ノードの外側ならその位置へそのまま挿入し、何かの内側だった場合は、それがトップレベルの段落かどうかを`resolve(pos).depth{:ts}`で確かめます。

```ts title="トップレベルの段落かどうかを確かめる"
const isTopLevelParagraphAt = (view: EditorView, pos: number) => {
  const { state } = view

  const node = state.doc.nodeAt(pos - 1)
  if (!node) return false
  if (node.type.name === "text") return false

  const depth = state.doc.resolve(pos).depth

  return node.type.name === "paragraph" && depth === 1
}
```

書きかけの段落やリストの項目を巻き込んでセクションに変えてしまわないように、判断のつかない位置では`false{:ts}`を返しています。

### セクション単位で入れ替える

視点カードを使わず、普通のMarkdownエディタとして書き始めることもできます。書いた後から任意の選択範囲をセクション化したり、セクションを解除する操作は、ツールバーのボタン1つで切り替わります。

<video muted playsinline controls preload="none" poster="/poster/summario-dev/drag-section-block_poster.png">
  <source src="/movie/summario-dev/drag-section-block.webm" type="video/webm" />
</video>

セクションにまとめておくと、見出しと本文をセットにしたまま並び替えられます。一般的なブロックエディタでは見出しと段落が別々のブロックになることが多く、章ごと入れ替える操作が欲しかったのです。

これを実現しているのは、中に複数のブロックを持てる`draggable{:ts}`なTiptapノードです。並び替えの単位となるTiptapノードを1つ用意するだけで、中身が何行あってもまとめて動くようになります。

```ts title="セクションのノード定義（抜粋）"
export const SectionBlockNode = Node.create({
  name: SECTION_BLOCK,
  group: "section",
  content: "block*",
  draggable: true
  // ...
})
```

ツールバーのボタンは、1つのTiptapコマンドで「セクションにまとめる」と「セクションを解除する」を兼ねています。今カーソルがあるのがセクションの中か外かで、どちらの動作を行うべきかを判定します。

```ts showLineNumbers {12,17} title="セクション化かセクション解除を行うコマンド"
toggleSectionBlock: () =>
  ({ chain }) => {
    const editor = this.editor

    // セクションブロックが1つもなければ通常の wrap を試みる
    if (!hasAnySectionBlock(editor)) {
      return chain().toggleWrap(SECTION_BLOCK).run()
    }

    const activeSectionBlock = getActiveSectionBlock(editor)

    // セクション外：現在の選択位置を基準に wrap
    if (!activeSectionBlock) {
      return wrapAtSelection(editor, chain)
    }

    // セクション内：子コンテンツ全体を選択して unwrap
    return unwrapActiveSectionBlock(chain, activeSectionBlock)
  }
```

セクションを解除する際、一旦、子コンテンツ全体を選択し直しています。セクションの中で選択されているのは普通1行だけなので、そのまま`toggleWrap(){:ts}`を呼ぶと、その1行だけが外へ出てしまいます。セクションの内側にあたる範囲を選び直してから外し、最後にキャレットを元の位置へ戻しています。

```ts showLineNumbers {3-4,10,12} title="セクションを解除する"
const contentRangeOfNode = (pos: number, node: PMNode) => {
  // 内部コンテンツだけを選択（自身の先頭+1 〜 自身の末尾-1）
  const from = pos + 1
  const to = pos + node.nodeSize - 1
  return { from, to }
}

const unwrapActiveSectionBlock = (chain: () => ChainedCommands, active: { pos: number; node: PMNode }) => {
  const { from, to } = contentRangeOfNode(active.pos, active.node)
  return chain()
    .setTextSelection({ from, to })
    .toggleWrap(SECTION_BLOCK)
    .setTextSelection(from) // キャレットを元の位置に戻す
    .run()
}
```

`nodeSize{:ts}`には、そのProseMirrorノードを開いて閉じるぶんの位置も含まれます。前後を1ずつ削った範囲が中身にあたるので、そこを選択してから`toggleWrap(){:ts}`を呼びます。

セクションは意味のあるまとまりである必要はなく、並び替えのために一時的に括るだけの使い方もできます。

## タイトルから始まる文書構造

ノートの編集には[Tiptap](https://tiptap.dev/)を使っていますが、何でも自由に書けるテキストエリアにはせず、文書の骨格を[ProseMirror](https://prosemirror.net/)のスキーマとして固定しています。

```ts title="ドキュメントのスキーマ定義"
const CustomDocument = Document.extend({
  content: "title aliases (section|block)*"
})
```

先頭には必ずタイトルが1つ、その次に別名の入力欄が来て、それ以降にセクションや通常のブロックが並ぶ、という構造です。Tiptapが土台にしているProseMirrorでは、ProseMirrorスキーマに反する構造のコンテンツはそもそも作れないため、タイトルを消してしまったノートや、タイトルが2つあるノートは発生しません。

- [ProseMirrorの文書構造を知る](/tech/summario-dev/tiptap-document)

ここで書いている`title{:ts}`や`aliases{:ts}`は、Tiptapのカスタムノード側で`group{:ts}`として宣言した名前を指しています。タイトルを`group: "block"{:ts}`にしてしまうと、ProseMirrorスキーマの`(section|block)*{:ts}`にも当てはまってしまい、文書のどこにでもタイトルを置けることになってしまいます。

```ts showLineNumbers {4} title="タイトルのノード定義"
export const TitleBlockNode = Node.create({
  name: TITLE_BLOCK,
  // group:"block"にしてしまうと、CustomDocument.contentの定義上、複数のtitle_blockが許容されてしまう
  group: "title",
  content: "inline*",
  marks: "code",
  parseHTML() {
    return [{ tag: "title-block" }]
  },
  renderHTML() {
    return ["h1", { class: "node-title_block" }, 0]
  }
})
```

本文で使える見出しも`h2{:html}`から`h4{:html}`に限定しました。`h1{:html}`はタイトル専用です。1テーマ1ノートという前提を、書ける構造の側から支えています。

タイトルの下にある別名の入力欄は、Tiptapのカスタムノードとして本文の中に埋め込んだ[Mantine](https://mantine.dev/)のタグ入力UIです。1つのテーマに複数の呼び名があることは珍しくないため、タイトルとは別に登録できるようにしています。

## 関連を先に登録してから書く

ノートの右側には、そのテーマと関連する他のテーマを登録する欄と、登録した関係をネットワークグラフとして描く==関連グラフ==があります。

  <source src="/movie/summario-dev/related-graph-and-miniview.webm" type="video/webm" />
</video>

[Obsidian](https://obsidian.md/)のグラフ機能は本文中の内部リンクから関係を組み立てますが、Summarioでは関連を明示的に登録する形にしました。本文を書くより先に関係だけを捉えておきたい場面が、自分の中にあったからです。

関連付けたいテーマは同じフォルダの中にあることが多いので、登録欄の候補は今いるフォルダのテーマから先に並ぶようにしました。

```ts title="関連テーマの候補を「フォルダの近さ」で並べ替えるクエリ（抜粋）"
const query = sql`
  SELECT id, title
  FROM ${terms}
  WHERE id <> ${excludeTermId}
  ORDER BY
    CASE
      WHEN ${currentFolderId}::int IS NULL AND folder_id IS NULL THEN 0
      WHEN ${currentFolderId}::int IS NOT NULL AND folder_id = ${currentFolderId} THEN 0
      ELSE 1
    END,
    folder_id;
`
```

### 無向グラフを片側だけ持つ

「AはBに関連する」と「BはAに関連する」は、Summarioでは同じ1つの事実です。両方向を別々の行として持つと、片方だけが消えた状態を作れてしまうため、関連は片側だけを保存することにしました。

```ts showLineNumbers {12} title="関連のテーブル定義"
export const termEdges = pgTable(
  "term_edges",
  {
    sourceTermId: integer("source_term_id")
      .references(() => terms.id, { onDelete: "cascade" })
      .notNull(),
    targetTermId: integer("target_term_id")
      .references(() => terms.id, { onDelete: "cascade" })
      .notNull(),
    createdAt: timestamp("created_at", { withTimezone: true }).defaultNow().notNull()
  },
  (t) => [primaryKey({ name: "pk_term_edges", columns: [t.sourceTermId, t.targetTermId] })]
)
```

主キーは2列の複合キーです。ただし、これだけでは`(1, 2){:sql}`と`(2, 1){:sql}`が別の行として通ってしまいます。そこで、挿入する前に必ずidの小さい方を`source_term_id{:sql}`へ揃えます。向きを捨てて、行の形を1通りに決めてしまう方針です。

```ts title="挿入前に(min, max)へ正規化する"
const edgeValues = relatedTermIds.map((relatedId) => {
  const [sourceTermId, targetTermId] = termId < relatedId ? [termId, relatedId] : [relatedId, termId]
  return { sourceTermId, targetTermId }
})
```

正規化した上で`ON CONFLICT DO NOTHING{:sql}`を付ければ、すでに登録済みの関連をもう一度登録しても、行は増えません。

そして、追加した関連は、画面へ返すときに「相手側のノート」の名前が必要になります。挿入した行から相手側のidを取り出し、もう一度`terms{:sql}`を引きに行くと2往復です。Drizzleは`INSERT ... RETURNING{:sql}`をそのままCTEにできるので、1つの文にまとめました。

```ts showLineNumbers {8-13} title="挿入と、相手側ノートの取得を1文にまとめる"
const ins = db.$with("ins").as(
  db
    .insert(termEdges)
    .values(edgeValues)
    .onConflictDoNothing()
    .returning({
      otherId: sql<number>`
        CASE
          WHEN ${termEdges.sourceTermId} = ${termId} THEN ${termEdges.targetTermId}
          ELSE ${termEdges.sourceTermId}
        END
      `.as("otherId")
    })
)

const rows = await db
  .with(ins)
  .selectDistinct({ id: terms.id, title: terms.title })
  .from(terms)
  .where(inArray(terms.id, db.select({ id: ins.otherId }).from(ins)))
```

`CASE{:sql}`で「自分ではない方のid」を返しているのは、正規化の結果、自分が`source{:sql}`側に来るか`target{:sql}`側に来るかが決まらないためです。削除も同じ形で、`DELETE ... RETURNING{:sql}`をCTEにして、消えた関連の相手だけを返しています。

読み取り側では、向きを気にせず両側から引きます。

```ts title="どちら側に入っていても取り出せる結合条件"
.innerJoin(
  termEdges,
  or(
    and(eq(termEdges.sourceTermId, terms.id), eq(termEdges.targetTermId, termId)),
    and(eq(termEdges.targetTermId, terms.id), eq(termEdges.sourceTermId, termId))
  )
)
```

### グラフの描画はライブラリに任せる

関連グラフの描画には[vis-network](https://github.com/visjs/vis-network)を使っています。Reactのコンポーネントとして宣言的に書けるライブラリではないので、`useEffect{:ts}`の中で`Network{:ts}`を組み立て、`ref{:ts}`で確保した要素へ描かせる形になります。

```ts showLineNumbers {4} title="中央ノードだけ見た目を変える"
visNodesRef.current = new DataSet(
  [centerNode, ...nodes].map((node) => ({
    id: node.id,
    label: node.id === centerNode.id ? editedCenterNodeTitle || centerNode.title : node.title,
    shape: "dot",
    size: node.id === centerNode.id ? 20 : 12
  }))
)
```

中央に置いたvis-networkのノードは、今開いているノート自身です。そのラベルには、保存済みのタイトルではなく、エディタで編集中のタイトルを優先して出しています。タイトルを打ち替えた瞬間にグラフのラベルも変わるので、保存前でも「今どのノートを見ているか」が食い違いません。タイトルの変化を検知する仕組みを軽く保ちたかったのは、この反映を打鍵のたびに走らせるためでもあります。

### ミニビューはサーバー側で組み立てる

グラフのノードをクリックすると、その下の==ミニビュー==にノートの本文が表示されます。関連するテーマと見比べながら書き進めるための機能で、中央のノードをクリックすれば、今開いているノートを最後に保存した時点の状態を見ることもできます。

読むためだけにもう一つエディタを立ち上げるのは重いので、`@tiptap/static-renderer{:ts}`にエディタと同じTiptap Extensionの構成を渡し、サーバー側でHTMLを組み立てています。

```ts title="サーバー側でノートをHTMLへ変換する"
const term = await getTerm(Number(params.termId))
const initialJSON = createPreviewJson(term.title, term.content as JSONContent[])

const html = renderToHTMLString({
  content: initialJSON,
  extensions: tiptapExtensions({ initialJSON })
})
```

渡すJSONはタイトルと本文だけを組み直したもので、編集用の別名入力欄は外しています。同じTiptap Extensionから生成しているので、本文の見た目はエディタとそのまま揃います。

フォルダの階層は==隣接リストモデル==でテーブルに持たせています。

隣接リストモデルは、階層を表す行が自分の親のidだけを持つ形です。木の形を1枚のテーブルで表す方法として最も素直で、フォルダを別の場所へ移す操作も`parent_id{:sql}`を書き換えるだけで済みます。

```ts showLineNumbers {5,12,14} title="フォルダのテーブル定義"
export const folders = pgTable(
  "folders",
  {
    id: serial("id").primaryKey(),
    name: varchar("name", { length: 255 }).notNull(),
    parentId: integer("parent_id"),
    createdAt: timestamp("created_at", { withTimezone: true }).defaultNow().notNull(),
    updatedAt: timestamp("updated_at", { withTimezone: true }).defaultNow().notNull()
  },
  (t) => [
    // 同階層（親が同じ）での重名禁止
    unique("uniq_folders_parent_name").on(t.parentId, t.name),
    // ツリー系のCTE探索を速くする補助（parent_id 用）
    index("idx_folders_parent").on(t.parentId)
  ]
)
```

ルート直下のフォルダは、親がいないので`parent_id{:sql}`が`NULL{:sql}`になります。この`NULL{:sql}`の扱いが、後述のクエリで一手間になります。

同じ階層に同じ名前のフォルダが並ぶと、どちらに入れたのか分からなくなるので、ファイルシステムと同じ感覚で使えるよう`(parent_id, name){:sql}`に一意制約を張りました。

代わりに、階層をまたいだ問い合わせは1回のクエリで完結しません。「このフォルダの上をルートまで辿る」といった操作は、親を1段ずつ遡る必要があります。

### NULLを含む階層を辿るSQL

直下だけを表示するクエリは、素直に書けば`WHERE parent_id = $1{:sql}`です。しかし、これでは一番上の階層を表示できません。ルート直下のフォルダは`parent_id{:sql}`が`NULL{:sql}`で、SQLの`={:sql}`は`NULL{:sql}`同士を等しいと判定しないからです。

ルート用のクエリを別に用意すると、同じ内容の分岐が呼び出し側に増えていきます。そこで`IS NOT DISTINCT FROM{:sql}`を使い、`NULL{:sql}`も1つの値として比較させました。

```ts showLineNumbers {10} title="直下のフォルダと、その中の件数を取得するクエリ"
const query = sql`
  WITH folders_with_counts AS (
    SELECT
      f.id, f.name, f.parent_id,
      -- 直下のファイル数
      (SELECT COUNT(*) FROM ${terms} t WHERE t.folder_id = f.id)::int AS file_count,
      -- 直下のフォルダ数
      (SELECT COUNT(*) FROM ${folders} c WHERE c.parent_id = f.id)::int AS folder_count
    FROM ${folders} f
    WHERE f.parent_id IS NOT DISTINCT FROM ${parentId}
  )

  SELECT
    id, name, parent_id,
    (file_count + folder_count) AS entry_count
  FROM folders_with_counts
  ORDER BY name;
`
```

一覧には「このフォルダの中にいくつ入っているか」を出したいので、相関サブクエリで直下のノート数とフォルダ数を数え、CTEの外で足しています。中身が空かどうかは、そのフォルダを削除してよいかの判断にも使います。

CTE（Common Table Expression）は、`WITH{:sql}`句でクエリの中だけに通用する名前を付けた、一時的な結果のまとまりです。ここでは、件数を数える処理を`folders_with_counts{:sql}`という名前で切り出しておき、外側では足し算と並べ替えだけを行っています。1つの`SELECT{:sql}`に詰め込むより、何をしているクエリなのかが追いやすくなります。

エディタの上に出るパンくずは、逆に葉から根へ遡ります。隣接リストモデルでは1行が親しか知らないので、ここは再帰CTEの出番です。

```sql showLineNumbers title="葉から根へ遡ってパスを組み立てる"
WITH RECURSIVE chain AS (
  -- アンカー：ファイルの親フォルダ（葉側）
  SELECT fo.id, fo.parent_id, fo.name, 1 AS depth
  FROM folders fo
  WHERE fo.id = $1

  UNION ALL

  -- 親へさかのぼる
  SELECT p.id, p.parent_id, p.name, c.depth + 1
  FROM folders p
  JOIN chain c ON c.parent_id = p.id
)

SELECT id, name
FROM chain
ORDER BY depth DESC; -- ルート(最大depth) → … → 葉(最小depth)
```

深さを数えながら遡り、最後に`depth{:sql}`の降順で並べ直すと、ルートから順に並んだパスになります。

こうしたクエリは、ORMのAPIだけで書くより生のSQLとして読めた方が意図が伝わります。APIと生SQLを同じコードの中で行き来できることが、DrizzleをORMに選んだ理由でもありました。

### 最初の一画面はサーバーで、その先はクエリで

エクスプローラは、フォルダ名をクリックするたびに表示を切り替えます。最初の表示までサーバーの往復を待たせたくはありませんが、その後の移動のたびにページ全体を読み込み直すのも過剰です。

そこで、[React Router](https://reactrouter.com/) v7のFramework Modeを使い、最初の一画面分はページの`loader{:ts}`で用意し、それ以降は[TanStack Query](https://tanstack.com/query/latest)がAPIを叩く形にしました。APIはReact RouterのResource Routesとして、`loader{:ts}`だけをexportするファイルで書いています。

```ts showLineNumbers {6,8} title="表示中のフォルダをキーにしてデータを取得する"
// TanStack Queryによるデータ取得
const { data, isPending, isError } = useQuery({
  queryKey: folderKeys.children(`${folderId}`),
  queryFn: () => fetch(`/api/folders/${folderId}/children`).then((res) => res.json()),
  refetchOnWindowFocus: false,
  staleTime: Infinity,
  enabled: folderId !== null,
  placeholderData: initials
})
```

`placeholderData{:ts}`に`loader{:ts}`が返した初期データを渡しているので、最初の描画ではAPIを待ちません。一度見たフォルダはキャッシュに残り、`staleTime: Infinity{:ts}`にしてあるため、行ったり来たりしても再取得は起きません。編集中に勝手に内容が入れ替わってほしくないので、ウィンドウのフォーカスによる再取得も切っています。

TanStack Queryによるデータ取得で使うキーは1箇所にまとめ、階層構造を持たせています。

```ts title="クエリキーの定義"
export const folderKeys = {
  all: ["folders"] as const,
  details: () => [...folderKeys.all, "detail"] as const,
  detail: (id: number | string) => [...folderKeys.details(), id] as const,
  children: (id: number | string) => [...folderKeys.detail(id), "children"] as const
}
```

たとえば、フォルダの移動が成功したときは`folderKeys.details(){:ts}`でフォルダ関連をまとめて作り直し、あわせて開いているノートのパスのキーも無効化して、パンくずの表示を追随させています。

## 保存するのは差分だけ

1回の保存で、本文・別名・関連テーマという性質の違うデータを同時に更新することになります。毎回すべてを送って洗い替えると、変わっていないものまで書き換えてしまうため、保存するのは差分だけにしました。

差分は[Jotai](https://jotai.org/)の派生Atomとして導出しています。サーバーから受け取った状態と、画面上で編集されている状態の差集合を取るだけの小さなAtomを用意し、そこから「追加する分」と「削除する分」を組み立てます。

```ts showLineNumbers title="差分を導出する派生Atom"
export const deriveDiffAtom = <T extends string>(
  debugLabel: string,
  getLeft: (get: Getter) => Iterable<T>,
  getRight: (get: Getter) => Iterable<T>
) => {
  const atom$ = atom<T[]>((get) => {
    const left = new Set(getLeft(get))
    const right = new Set(getRight(get))
    return [...left].filter((name) => !right.has(name))
  })
  atom$.debugLabel = debugLabel
  return atom$
}
```

引数の順序を入れ替えるだけで、追加分と削除分の両方を同じ関数から作れます。

```ts title="追加分と削除分を同じ関数から作る"
// 追加：UIにあるが serverData には無い
export const toAddRelatedTermLabels$ = deriveDiffAtom(
  "toAddRelatedTermLabels",
  (get) => get(uiRelatedTermLabel$),
  (get) => get(serverRelatedTerm$).keys()
)

// 削除：serverData にはあるが UI には無い
export const toRemoveRelatedTermLabels$ = deriveDiffAtom(
  "toRemoveRelatedTermLabels",
  (get) => get(serverRelatedTerm$).keys(),
  (get) => get(uiRelatedTermLabel$)
)
```

保存ボタンが押せるのは、本文・別名・関連テーマのいずれかに差分があり、かつタイトルが空でないときだけです。本文が編集されていなければ、本文の欄には`null{:ts}`を送ります。

### 部分的な失敗を許す

差分を送ると、サーバー側では最大5つの更新（本文、別名の追加と削除、関連の追加と削除）が並びます。これを1つのデータベーストランザクションにまとめて、どれか1つ失敗したら全部なかったことにする、という作り方はしませんでした。個人用のノートアプリで、本文は保存できたのに別名の削除だけ失敗したとき、本文まで巻き戻る方が困るからです。

そこで、実行すべき更新を配列にまとめ、`Promise.allSettled(){:ts}`で並行に走らせています。

```ts showLineNumbers title="更新をタスクとして並べる（抜粋）"
const tasks: SavingTask[] = [
  {
    key: "content",
    condition: content !== null,
    action: () => TermService.updateTermContent(termId, title, content!),
    targets: termId
  },
  {
    key: "alias.add",
    condition: alias.add && alias.add.length > 0,
    action: () =>
      AliasService.addAliases(
        termId,
        alias.add.map((a) => a.title)
      ),
    targets: alias.add
  }
  // ...
]

const results = await Promise.allSettled(tasks.map((t) => (t.condition ? t.action() : Promise.resolve([]))))
```

`SavingTask{:ts}`は`key{:ts}`で分岐する判別可能なユニオンです。`key{:ts}`が`"alias.add"{:ts}`なら`targets{:ts}`は追加しようとした別名の配列、`"content"{:ts}`ならノートのidというように、失敗したときにメッセージへ載せられる情報の型が`key{:ts}`ごとに決まります。

```ts title="失敗した項目だけを取り出すための型"
type DistributivePick<T, K extends keyof T> = T extends any ? Pick<T, K> : never
export type SaveRejected = DistributivePick<SavingTask, "key" | "targets"> & { reason: unknown }
```

`Pick{:ts}`をそのままユニオンに当てると、`key{:ts}`と`targets{:ts}`の組み合わせが崩れて総当たりになってしまいます。`T extends any ? ... : never{:ts}`と書いてユニオンの要素ごとに`Pick{:ts}`を分配し、対応関係を保ったままにしています。

あとは、失敗した`key{:ts}`をメッセージへ変換し、画面ではトーストとして1件ずつ出します。「別名の追加に失敗しました」のように、どのデータのどの操作が失敗したかが分かり、成功した分はそのまま保存済みとして扱えます。エクスプローラのフォルダ移動が種類ごとに結果を返しているのも、同じ考え方によるものです。

### 保存中の編集を落とさない

=保存は非同期なので、通信が返るまでの間にも本文は編集できます。返ってきたときに一律で未編集の状態へ戻してしまうと、その間の編集が保存されないまま、保存済みという表示になってしまいます。

そこで、dirty（未保存の変更があるか）を管理するTiptap Extensionを自作しました。基準となる文書を持ち、ProseMirrorのトランザクションが起きるたびに現在の文書と比較します。ProseMirrorノードは不変なので、参照を持っておくだけで比較できます。

```ts title="保存の前後で使うコマンド"
markClean: () => ReturnType // 今のドキュメントを基準（未編集）にする
takeSnapshot: () => ReturnType // 現在docを内部にスナップショット
markCleanIfUnmodified: () => ReturnType // スナップショットと一致していれば未編集化
```

保存ボタンを押した時点で`takeSnapshot(){:ts}`を呼び、レスポンスが返ってきたら`markCleanIfUnmodified(){:ts}`を呼びます。一致していれば未編集に戻り、一致しなければ`false{:ts}`が返るので、そのときは「保存中に編集されました。もう一度保存してください。」と伝えます。

タイトルの監視にも、似た考え方の最適化を入れました。ヘッダーの表示や保存ボタンの活性はタイトルの変化に反応しますが、本文を打つたびに文書全体を走査したくはありません。

```ts showLineNumbers {5-6} title="先頭ノードに触れたトランザクションだけを見る"
apply(tr, _v, _oldState, newState) {
  if (!tr.docChanged) return null

  // 旧docの先頭ノード範囲に触れていなければスキップ（先頭見出しは不変とみなす）
  const touched = mappingTouchesRange(tr, 0, Math.max(0, prev.firstNodeSize))
  if (!touched) return null

  // 触れている／またはサイズ不明なときだけ読み直す（O(1)）
  const next = readTopTitle(newState)
  // ...
}
```

ProseMirrorのトランザクションは、変更が旧文書のどの範囲にあたるかを`StepMap{:ts}`として持っています。それを使って先頭のProseMirrorノードの範囲と重なるかどうかだけを判定し、重なったときだけ先頭の子ノードを読みます。文書の何行目を編集していても、判定にかかる手間は変わりません。

## 依存の向きをルールとして書く

プロトタイプとはいえ、機能を足すたびにどこへ何を書くか迷うのは避けたくて、ディレクトリの役割と依存の向きを先に決めました。

- `app/units{:bash}`：1つのオブジェクトで完結するロジック
- `app/usecases{:bash}`：複数のオブジェクトにまたがり、データの書き換えを伴う機能
- `app/queries{:bash}`：複数のオブジェクトにまたがる読み取り

読み取りと書き込みで通る経路も分けました。書き込みは`repository{:bash}`から`service{:bash}`、`feature{:bash}`へ、読み取りは`readstore{:bash}`から`reader{:bash}`へと順に通ります。

UIの状態も同じ考え方で、JotaiのAtomを役割ごとにファイルへ分けています。

- `ui.atoms.ts{:bash}`：状態そのもの
- `ui.selectors.ts{:bash}`：状態から算出される値（派生Atom）
- `ui.actions.ts{:bash}`：状態に変更を加える操作（書き込み専用Atom）
- `ui.hooks.ts{:bash}`：コンポーネントへ公開するReactのカスタムフック

差分の導出や、保存ボタンを押せるかどうかの判定を`ui.selectors.ts{:bash}`へ寄せているのは、コンポーネントに計算を持たせないためです。コンポーネントから見えるのはフックが返す値だけなので、判定の中身を変えても呼び出し側は書き換わりません。この境界もルールとして書いてあります。

```js title="コンポーネントからAtomの内部へ触らせないルール"
{
  name: "components-cannot-touch-ui-internals",
  severity: "error",
  from: { path: "^app/components/" },
  to: {
    path: "^app/(units|usecases)/[^/]+/ui\\.(atoms|selectors|actions)\\.ts$"
  }
}
```

読み取りを`units{:bash}`の`service{:bash}`に相乗りさせなかったのは、画面ごとに欲しい形が違うからです。1つのノートを開くだけでも、本文・別名・関連・パンくず・フォルダの中身と、複数のオブジェクトを跨いだ組み立てが必要になります。

```ts title="1画面ぶんのデータを組み立てるreader"
export const getTermWithMeta = async (id: number) => {
  const [term, alias, related] = await Promise.all([
    TermService.getTerm(id),
    AliasService.getAliases(id),
    RelatedTermService.getRelatedTerms(id)
  ])

  return { term, alias, related }
}
```

サーバー専用のファイルには`.server.ts{:bash}`を付けて、クライアントのバンドルに混ざらないようにしています。

こうした取り決めは、決めた本人でも時間が経てば忘れます。そこで[dependency-cruiser](https://github.com/sverweij/dependency-cruiser)を導入し、守りたい依存の向きを10本のルールとして書き下しました。

```js showLineNumbers title="データベースに触れてよいファイルを限定するルール"
{
  name: "db-access-only-from-repository-or-readstore",
  severity: "error",
  from: {
    pathNot:
      "^(?:app/units/[^/]+/repository\\.server\\.ts|app/queries/[^/]+/readstore\\.server\\.ts)$"
  },
  to: { path: "^app/db(/|$)" }
}
```

`from{:js}`に`pathNot{:js}`を書くと、「ここに挙げたファイル以外から`app/db{:bash}`へ依存したらエラー」という意味になります。

同じ書き方で、層をまたぐ呼び出しを禁じるルールを並べています。

- `repository{:bash}`を呼べるのは`service{:bash}`だけ
- `readstore{:bash}`を呼べるのは`reader{:bash}`だけ
- `service{:bash}`と`feature{:bash}`はUIやルーティングを参照しない
- `usecases{:bash}`配下、`queries{:bash}`配下のディレクトリ同士は依存しない
- APIのファイルは`reader{:bash}`と`feature{:bash}`だけを経由する

`npm run deps-check{:bash}`で違反を検出でき、`npm run deps-graph{:bash}`では依存関係を可視化したグラフをSVGとして出力できます。設計意図をドキュメントとして書き残すより、壊れたときに気づける形にしておく方が、一人で長く続ける上では確実だと感じています。

## エディタの挙動はブラウザで確かめる

Tiptapに追加した独自の機能は、キャレットの位置や文書内の位置計算に踏み込むものが多くあります。ドロップされた座標がどのProseMirrorノードの内側にあたるのか、削除した後にキャレットをどこへ戻すのか、といった判断は、実際に描画された文書の上でしか確かめられません。

そこで[Vitest](https://vitest.dev/)の`projects{:ts}`機能を使い、Node上で動かすテストと、ブラウザ上で動かすテストを分けました。

```ts showLineNumbers title="テストを2つのプロジェクトに分ける"
projects: [
  {
    test: {
      include: ["app/**/*.{test,spec}.ts"],
      exclude: ["app/**/*.browser.{test,spec}.ts"],
      name: "script",
      environment: "node"
    }
  },
  {
    test: {
      include: ["app/**/*.browser.{test,spec}.ts"],
      name: "browser",
      browser: {
        enabled: true,
        provider: playwright(),
        instances: [{ browser: "chromium" }]
      }
    }
  }
]
```

ファイル名に`.browser{:bash}`が入っているかどうかで振り分けられるので、テストを書き足すときに設定を触る必要がありません。ブラウザ側は[Playwright](https://playwright.dev/)でChromiumを起動し、本物のエディタをマウントしてから操作を検証します。

現時点では26件のテストがあり、次のような分岐を固定しています。

- 視点カードのドロップ位置による挙動の違い（ブロックの間、トップレベルの空段落、リストや引用の中）
- 削除操作の対象（タイトル行は内容のクリアのみ、リストは項目ごと、セクションは子が1つなら丸ごと）
- 削除した後にキャレットが戻る位置
- セクションのラップとアンラップ

## フォルダ構造をマインドマップとして編集する

ここまでのフォルダ機能は手元を辿るためのものですが、全体の中でどこに属するかを見ながら、構造そのものを編集したい場面もあります。そのための==構造マップ==を、[React Flow](https://reactflow.dev/)と[dagre](https://github.com/dagrejs/dagre)による自動整列で作っています。

フォルダとノートがReact Flowのノードになり、フォルダの親子関係とフォルダ内のノートがエッジとして描かれます。名前を入力してからマップへドラッグすると新しいノードが増え、ノード同士を線で結ぶと親子関係になります。本文のあるノートは、マップ上では名前の変更も削除もできません。全体を眺めている最中の操作で本文を失いたくないからです。

その判断はサーバー側で済ませていて、ノードを組み立てる時点で削除可否を決めています。

```ts showLineNumbers {8} title="ノードの削除可否をサーバー側で決める（抜粋）"
const termNodes = terms.map((term) => {
  const isContentEmpty = judgeContentEmpty(term.content as JSONContent[])
  return {
    id: createFileNodeId(term.id),
    data: { label: term.title, isContentEmpty, tmp: false },
    position: TMP_POSITION,
    type: FILE_NODE_TYPE,
    deletable: isContentEmpty
  }
})
```

ノードのidは、`term-{:bash}`と`folder-{:bash}`のプレフィックスで種類を区別しています。React Flowが扱うidは文字列である一方、ノートとフォルダのidはそれぞれ別の連番なので、そのまま混ぜると衝突するためです。ノートのノードから編集ページへ移動するときは、このプレフィックスを外して数値のidに戻します。

親子関係の制約は、React Flowのハンドルの接続数として表しました。

```tsx showLineNumbers {7} title="1つのノートが2つの親にぶら下がらないようにする"
const MAX_CONNECTIONS = 1

const FileNodeHandle = ({ type }: FileNodeHandleProps) => {
  const connections = useNodeConnections({ handleType: type })
  return (
    <Handle
      type={type}
      position={type === "target" ? Position.Left : Position.Right}
      isConnectable={connections.length < MAX_CONNECTIONS}
      className={styles.handle}
    />
  )
}
```

すでに線が1本つながっているハンドルは`isConnectable{:ts}`が`false{:ts}`になり、2本目を引けません。ノートが属せるフォルダは1つだけ、という制約を、線を引く操作の側から守っています。

現時点では、この画面での操作はブラウザの中で完結していて、結果をデータベースへ書き戻すところまでは実装できていません。エクスプローラ側の操作が1つずつのAPI呼び出しで完結するのに対して、マップ上ではノードの追加・削除・線の張り替えが混ざった状態でまとめて確定することになります。その差分をどう表現し、どの順序で流すのかを決めきれていません。

ここを実装しきって、全体像を描いてから詳細を埋める流れと、詳細をまとめてから繋げる流れの両方を1つのアプリで完結させることが、このプロトタイプで確かめたい最後のところです。
