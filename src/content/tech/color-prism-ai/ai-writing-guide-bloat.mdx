[AIに文章を書く思考回路を模倣させる](/tech/color-prism-ai/ai-mimic-writing-thought-process)で書いた、analyzerとwriterという2つのスキルによる文章生成の仕組みは、その後も記事を分析するたびにスタイルガイドを育て続けてきた。

そして、writerが執筆のたびに読み込むスタイルガイドは、4ファイル計313,714字に達した。日本語は概ね1文字が1トークン前後なので、ガイドを開くだけで20万トークン級を消費する計算になる。記事本文を書く余地が残らない。

analyzerの差分更新は「既存ルールの確度欄と根拠欄に追記する」形で設計されていた。記事を分析するほど執筆側が重くなる構造で、しかも分析待ちの記事はまだ400本以上残っている。この構造を作り直したときの記録。

## ガイドが記事数に比例して太っていた

膨らんでいたのはルールの本数ではなく、1ルールあたりの文字数だった。

たとえば`writing-style.md`の「総括・まとめの節を設けない」というルールは、確度欄だけで3,201字ある。中身は「配色技法シリーズ10本すべてが…／混色シリーズ6本も…／デジタル画像シリーズ5本も…」という、分析回ごとの追記の連なりだ。執筆側にとっては「強い傾向」の一語で足りる。

242ルールすべてについて欄ごとに文字数を数えたら、次のようになった。

| 項目                     | 文字数 |  比率 |
| ------------------------ | -----: | ----: |
| 根拠                     | 82,442 | 27.1% |
| 確度                     | 57,321 | 18.9% |
| 関連ルール               | 34,237 | 11.3% |
| 反例・例外               | 26,073 |  8.6% |
| 適用する／しない状況     | 24,465 |  8.1% |
| ルール（本体）           | 24,370 |  8.0% |
| その他（対象・見出し等） | 54,806 | 18.0% |

実行可能な指示、つまりルール本体と適用条件は全体の16%しかない。66%は根拠・確度・関連ルール・反例という、分析のときにしか使わない情報だった。

`writing-style.md`の行数は、20回の分析ラウンドを通じて線形に増えていた。最終ラウンドでもなお`+59/−22`行。当時の分析済みは85記事で、まだページを作っていない記事が436本控えている。一度手で掃除しても、同じ速度で元に戻る。

=p=執筆側の量をルール数に比例させ、記事数に比例させない。==これを目標にした。

## 分割案をひととおり却下する

読む量を減らす方向として、まずガイドの分割を4つ検討して、全部やめた。

**ルールの統合・削減。** 85記事から242ルールは多く、統合の余地はある。ただし統合が妥当だったかは、統合した2ルールの根拠を読み比べないと検証できない。根拠を捨てる作業と同じラウンドで統合をやると、間違いに気づく手段のほうが先に消える。

**記事タイプ別の分割。** `writing-style.md`の78ルールのうち72件、92%が適用対象に「概念解説」を含んでいた。記事タイプの値自体も78ルールに対して41種類の自由記述で、機械的に振り分けられる状態ではない。

**確度別の分割。** 確度は「その特徴がどれだけ著者固有か」の指標であって、「どれだけ頻繁に使うか」の指標ではない。確度で割ると`refine-style.md`の核が3ルールしか残らず、編集モードで最もよく効く「箇条書き→散文」や「指示語・主語の明示化」が条件付き側へ落ちてしまう。

**索引だけ読ませて、writerに必要なルールを選ばせる進行的開示。** スタイルガイドには「まとめの節を置かない」のような==不在の制約==が多い。存在を知らない制約を索引から引くことはできない。

残ったのは、ルールの本数も分け方も変えずに、1ルールあたりの文字数を落とす方向だけだった。

## 内容ではなく、誰が読むかで分ける

ファイルを分ける軸を、「何が書いてあるか」から「誰が読むか」に変えた。

writerが読むガイド本体に残すのは、実行可能なルールと適用条件、それに確度ラベル3語（`強い傾向`／`条件付きの傾向`／`弱い傾向`）だけ。根拠、確度の判定理由、保留中の観察は、すべてanalyzer専用のファイルへ移す。

```text title="誰が読むかで分けたファイル"
thinking-flow.md            ┐
writing-style.md            │ writerが読む
stylistic-quirks.md         │   実行可能なルール・適用条件・確度ラベル3語
refine-style.md             ┘
evidence/<観点>/<slug>.md   ┐ analyzerだけが読む
pending/<観点>.md           ┘   根拠・分析時点のSHA・保留中の観察
```

確度をラベルだけ残したのは、writerが「このルールをどのくらい強く当てるか」を知る必要があるからだ。強い傾向は既定で当て、条件付きの傾向は適用条件に合うときだけ当て、弱い傾向は積極的に適用しない。「なぜその確度なのか」のほうは、次の分析ラウンドで確度を上げ下げするときにしか使わない。

分離した根拠は、writerに読ませない。`pending/`（保留プール）と同じ強さで禁止している。理由は量ではなく、中身の性質にある。根拠ファイルはパスがそのまま記事のslugで、中身はその記事の該当箇所そのものだ。開けば特定の記事の言い回しをなぞることになり、「個別記事を文体の手本にしない」という方針と正面からぶつかる。

### モードごとに読む量を変える

分けたところで、writerが毎回4ファイル全部を読むなら効き目は半分になる。作業の種類によって、必要なガイドは違う。

| モード     | 読むガイド                                                        |
| ---------- | ----------------------------------------------------------------- |
| 生成       | `thinking-flow` `writing-style` `stylistic-quirks` `refine-style` |
| 推敲       | `writing-style` `stylistic-quirks` `refine-style`                 |
| 編集       | `stylistic-quirks` `refine-style`                                 |
| 編集・最小 | `refine-style`                                                    |

生成モードだけは削っていない。記事を新しく書き起こす作業では、何を説明するかの判断から表現の調整まで全層が要るので、読み込み量より品質を優先した。推敲で`thinking-flow.md`を外すのは、説明する内容そのものを設計し直さないからだ。ただし依頼が「構成から見直す」に及んだら、その時点で範囲を広げてよいことにしている。足りないまま推測で補われるほうが困る。

## 根拠を捨てる前に、埋もれた制約を引き上げる

根拠欄を消すだけなら、該当行を落とすスクリプトで済むはずだった。実際にはそれができなかった。

`stylistic-quirks.md`の「ヘッジ文末：主観・一般則を和らげる」というルールは1,893字あり、うち1,307字が根拠だった。

```markdown title="❌ 圧縮前（1,893字）"
### ヘッジ文末：主観・一般則を和らげる

- 表現：「〜傾向があります」「〜こともあります」「〜かもしれません」「〜でしょう」。
- ルール：一般則や主観的な色の印象を述べるときは断定せず、これらのヘッジ文末で和らげる。
- 使用目的：例外や個人差のある事柄で言い切りを避けつつ、確定した定義とはregisterを分ける。
- 適用しない状況：定義・表色系のルール・手順の指示は断定する。
- 確度：強い傾向（直接確認できる事実）。色の理論5記事以上で多数確認でき…（221字）
- 根拠：「異なる傾向があります」「大まかに明度を表すこともあります」／CG基礎
  「生じることがあります」…照明・光源シリーズでも…色覚シリーズは…（1,307字）
```

圧縮すると、約440字になる。

```markdown title="👍 圧縮後（約440字）"
### ヘッジ文末：主観・一般則を和らげる

- 確度：強い傾向
- 表現：「〜傾向があります」「〜こともあります」「〜かもしれません」「〜でしょう」。
- ルール：一般則・主観的な印象・例外や付随ケースを述べるときは断定せず、
  これらのヘッジ文末で和らげる。
- 適用しない状況：定義・分類・表色系のルール・手順の指示・装置や処理の機能説明は
  「〜です」「〜します」で断定する。確定した割合や分類も言い切る。
- 使用量：1段落に2回以上重ねない。
- 変種：著者自身の推測を述べる場面がない記事タイプでは、助動詞ヘッジを使わず、
  量化・程度限定の語で和らげる。
```

「使用量」と「変種」の2行は、圧縮前のルール欄にも適用条件欄にも書かれていなかった。1,307字の根拠の散文に埋もれていたものを引き上げている。「適用しない状況」も、圧縮前の「定義・表色系のルール・手順の指示」に、根拠から拾った「分類」「装置や処理の機能説明」「確定した割合」が加わって増えた。

「双方向の括弧グロス」というルールの根拠3,349字にも、括弧の中身は名詞句か短い述部に抑えて句点を打たない、1文に括弧注を2つ以上入れるのは対句のときだけ、といった制約が埋もれていた。

=p=根拠欄をスクリプトで機械的に切り落とすと、これらが一緒に消える。==

散文から実行可能な制約を見分けるのは意味の判断で、自動化できない。242ルールを1件ずつ読むことになり、ここが移行作業の本体になった。この引き上げを「昇格」と呼んでいる。

## 根拠を記事単位に持ち替える

根拠を別ファイルへ移すだけでは足りなかった。台帳がルール単位で組まれている限り、根拠の==撤回==ができない。

ある記事がひとつのルールを支持していて、その記事を改稿してルールが成り立たなくなったとする。そのルールの根拠から当該記事を外し、確度を数え直す必要がある。ところが「配色技法シリーズ10本すべてが〜」という集約表現からは、1本分だけ減らせない。

これは仮定の話ではない。`/color-fields/landscape-color-approach`は2026年7月19日に分析され、その9日後に本文が改稿されている。ガイドに載っていた同記事由来の根拠は、その時点ですでに現物と一致していなかった。

そこで、根拠を記事単位へ正規化した。`writing-guides/evidence/<観点>/<slug>.md`の1記事1ファイルで、ファイルパスがそのままslugに対応する。

```markdown title="evidence/refine-style/cg/basics/area-filling.md"
分析時点: `78ba48cd`
記事タイプ: 実装解説

- RS-023（16758df→78ba48c：交点が偶数個になる理由の段落を新設）
- RS-033（16758df→78ba48c：スキャンライン／シードフィル／偶数）
  ※ RS-027：導入と節末の予告文を一字一句変えずに残す
```

先頭の`分析時点`は、分析した本文のコミットの短縮SHA。現在の最終更新コミットと突き合わせれば、分析後に改稿された記事を機械的に洗い出せる。記事1本を再分析するときは、4観点ともその記事のファイルを丸ごと書き直すだけで、他の記事のファイルには触らない。

ルールの参照に`RS-023`のような安定IDを使っているのは、ルール名が人間の都合で変わるからだ。改名してもIDは据え置き、廃止したIDは欠番として残して再利用しない。人間向けの名前と機械向けのキーを分けている。

支持記事数はどこにも書かない。`style-evidence-tally.mjs`が根拠ファイルを数えて出す。=p=導出できる値を保存すると、記事が増えるたびにまた追記の対象になる。==昇格候補の抽出も、後で触れる肥大化率の測定も、同じ理由でスクリプト側に置いた。

## 分析を「根拠を集める」と「ルールを見直す」に分ける

analyzer側も同じ問題を抱えていた。記事を1本公開するたびに、ガイド本体を読み、ルールを書き換え、根拠を足すフルパイプラインが走っていた。

けれど「新しく書いた記事が既存ルールを支持するか記録する」ことと、「溜まった根拠からガイドを見直す」ことは、別の作業だ。そこで手順を2つに割った。既定は==根拠モード==で、`--discover`を付けると==発見モード==になる。

```bash
/author-style-analyzer #cg-basics              # 根拠モード（既定）
/author-style-analyzer #cg-basics --discover   # 発見モード
/author-style-analyzer --discover              # 棚卸しのみ（記事を読まない）
```

|                    | 根拠モード（既定）                 | 発見モード（`--discover`）         |
| ------------------ | ---------------------------------- | ---------------------------------- |
| 目的               | 記事が既存ルールを支持するかを記録 | ガイドそのものを見直す             |
| 書き込み先         | `evidence/`のみ                    | 本体・`evidence/`・`pending/`の3層 |
| ガイド本体         | 触らない（確度の降格を除く）       | 更新する                           |
| 新しい特徴         | `pending/`へ1行で積む              | 昇格・採用を判断する               |
| 境界レビュー       | 実行しない                         | 実行する                           |
| 記事指定なしの実行 | 不可                               | 可（棚卸しのみ）                   |
| エージェント数     | 8体（Git履歴なしなら6体）          | 10〜13体                           |

記事を公開した直後は根拠モードで足りる。軽く速く、ガイド本体が動かないので差分レビューも要らない。逆に、記事を追加せずガイドだけ整理したいときは`--discover`を単独で実行する。保留の昇格候補と支持記事数の集計だけで棚卸しが回る。

根拠モードで本体に触れる例外は、確度の降格だけにした。今回書き直した記事に関係するルールを数え直して、支持が2記事以下に落ちていたら`確度`欄を「弱い傾向」へ下げる。該当が無ければ本体は1文字も変わらない。

根拠モードが安く済む理由は2つある。ひとつは、統合エージェントを持たないこと。根拠の生成が判定結果からの機械的な写像に落ちるので、エージェントではなくスクリプトが書く。もうひとつは、ガイド本体をエージェントに読ませないこと。判定エージェントへ渡すのはルールID一覧の約1万字と記事本文だけで済む。`Edit`は同じ会話で読んだファイルしか編集できないので、エージェントに本体を書かせるなら本体を読ませることになる。書き込み先を記事単位の新規ファイルに落とすことで、この制約を迂回している。

発見モードにだけある「境界レビュー」は、統合が終わったあとに本体4ファイルを読んで、同じ特徴が別々のファイルへ重複していないか、配置先が観点とずれていないかを検出する後段の担当だ。修正はさせず、検出結果を報告して次のラウンドへ持ち越す。

=p=根拠モードでも発見は起きる。==変わるのは「見つけた特徴をその場で本体に入れるかどうか」だけだ。根拠モードでは`pending/`へ1行で積み、採用するかどうかの判断を発見モードにまとめる。発見の機会を捨てて軽くしているわけではない。

## 肥大化率を毎回測る

構造を変えただけでは、また同じことが起きる。差分更新である以上、追記はどこかへ向かう。

そこで分析ラウンドごとに`style-guide-size.mjs`を走らせ、ファイルごとの文字数の増減、増減率、ルール数を出すことにした。

```bash
node scripts/style-guide-size.mjs
```

```text title="根拠モードのラウンド後"
  ファイル                     文字数            増減   肥大化   ルール数
  thinking-flow.md      45,313 → 45,313            ±0      ±0%         61
  writing-style.md      57,227 → 57,227            ±0      ±0%         79
  stylistic-quirks.md   42,248 → 42,248            ±0      ±0%         77
  refine-style.md       29,826 → 29,826            ±0      ±0%         38
```

**ルール数が増えていないのに本文が5%以上膨らんだファイルは、スクリプトが警告する。**分析メタデータが本体へ漏れた疑いとして、報告の前に該当箇所を`evidence/`や`pending/`へ戻す。根拠モードのラウンドでは全ファイル`±0%`になるのが正常で、これがガイド本体を触っていないことの裏づけになる。

移行から何ラウンドか回して、いまガイド本体4ファイルは255ルールで174,614字。ルールは242本から13本増えている。文字数の増分がルール数に比例している限り、この構造は目標どおりに動いている。

ただ、増える先が本体から`pending/`へ移っただけ、という見方もできる。保留は368件溜まっていて、閾値の支持3記事を超えた昇格候補が42件出ている。根拠モードの完了報告にはこの2つの件数が必ず入り、閾値を超えていれば発見モードを回すよう促される。件数の集計はスクリプトがやってくれるが、昇格させるかどうかの判断は機械化できないので、ここは自分で読むしかない。

保留にしたルールの統合にも、まだ手を付けていない。`writing-style.md`の「単一の枠組み（比喩・対比軸）で記事全体を貫く」と「見出しが修辞関係を名指すことがある」は、同じ機構を別のレイヤーから言っているだけに見える。圧縮後のガイドで何本か書かせてから判断するつもりだったので、そろそろ決めてよい頃だと思う。

確度ラベルの付け方が観点間で揃っていないのも気になっている。`stylistic-quirks.md`は77ルール中15本が「強い傾向」なのに対し、`refine-style.md`は38ルール中2本しかない。writerはこのラベルだけを見て当てる強さを決めるので、同じ「強い傾向」がファイルによって違う意味になっていると、そのまま生成結果に出る。ラベルは残したが、意味づけまでは揃えられていない。
