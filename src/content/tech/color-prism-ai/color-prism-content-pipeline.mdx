[Color Prism](/projects/color-prism)の記事は、本文を書く作業だけでは1本にならない。一覧データのどこに置くかを決め、ページの雛形を起こし、本文からリンクする先を用意し、書き、図版とデモを足し、公開して、OGP画像を生成する。この流れをClaude Codeのスキルに割り振って、順に通す形にしている。

執筆そのものについては[AIに文章を書く思考回路を模倣させる](/tech/color-prism-ai/ai-mimic-writing-thought-process)と[AI執筆ガイドの肥大化と戦う](/tech/color-prism-ai/ai-writing-guide-bloat)で書いた。今回はその前後の話。文章を生成するところは工程の真ん中の一段でしかなくて、実際に手間がかかるのは前後の準備と後始末だった。

どのスキルも、自分の担当が終わったら次に叩くコマンドを案内して止まる。どこで止めるかは、私が決めたい判断がその先に残っているかどうかで決めている。

## 一覧の1行が記事の起点になる

Color Prismのコンテンツは「CG・画像処理」「色の理論」「色の活用分野」の3種類あり、どれも掲載順と掲載先は`app/src/lib/content-pages/`配下のYAMLが決めている。本文を書き始めるより先に、一覧のどこに並ぶかが決まっている。

一覧に載っている項目は、リンク先としての状態が3つに分かれる。

- ==下書きリンク==：YAMLに`title`だけのエントリがある。ルートが無いのでリンクできない
- ==雛形ページ==：`+page.svx`が`draft: true{:yaml}`と`## TODO`だけの状態で存在する。ルートがあるのでリンクできる
- 実装済みページ：本文がある

`/create-cg-page <ページタイトル>`を叩くと、下書きリンクが雛形ページに変わる。CGの一覧は`basics.yaml`・`rendering.yaml`のようにユニットごとにファイルが分かれていて、スキルは全YAMLからタイトルの一致するエントリを探し、そのファイル名をユニットのslugとして`app/src/routes/cg/<ユニット>/<slug>/+page.svx`を作る。同時に、YAML側のエントリを`- slug: <slug>{:yaml}`の1行へ置き換える。

日本語タイトルから英語のslugを考えるのはスキルの仕事だが、`# CG 1-2-1 / ImgP 2-4`のような行末コメント（教科書の対応章）は、YAMLから雛形のfrontmatterへそのまま書き写させている。文言・記号・スペースを改変するな、という条件付きで。私が後から検定の範囲を照らし合わせるための印なので、意味を汲んで整形されると困る。

雛形の中身は`## TODO`の1行だけで、本文は書かせない。この「本文が無いのにルートはある」という中間状態を挟んでいるのには理由がある。=p=本文が無くても、ルートさえあれば他の記事からリンクできる。==

## 本文を書く前にリンク先を揃える

記事を書いていると、本文に出てきた語のうちどれを他ページへのリンクにするかを決めることになる。この判断を執筆中にやると、リンクしたい語のページがまだ無いことに気づいて、そこで手が止まる。書き上げてから足すこともできるが、リンクできなかった語は本文に埋もれて、あとから拾い直すのが面倒になる。

そこで、執筆の前に`/prepare-link-targets <キーワード一覧>`を通すようにした。記事で扱う語を並べて渡すと、語ごとに4つへ分類される。

- **A**：記事自身が定義・説明する概念。別ページにしない
- **B**：既存ページが主題として扱っている。リンク先になる
- **C**：YAMLに下書きリンクはあるが、ルートが無い。雛形を起こす対象
- **D**：どのYAMLにも項目が無い。本文で吸収する

分類が終わると、キーワード・分類・リンク先・根拠を並べた表が出る。Cの項目とslug案について承認を取ってから、`create-cg-page`などの手順で雛形をまとめて起こす。

境目で迷うのはAとCで、「単独で1ページ立つ規模か」で見ることにしている。ただしCには「すでにYAMLにエントリがある」という条件を付けた。エントリが無ければ、規模に関わらずDになる。

Dの項目を自動でYAMLに足す案は却下した。一覧のどのユニットのどの節に置くかは掲載順の設計で、記事1本の都合で決めていいものではない。内積や判別式のような数学の前提知識は、このリポジトリに数学の単元が無いので必ずDに落ちるが、これは本文で吸収すればいい話であって、一覧に単元を新設する話ではない。だからDは報告だけにとどめて、YAMLは触らせない。

slug案には「兄弟項目は接尾辞を揃える」という条件も付けた。隠面消去の4手法なら`priority-algorithm`・`scanline-algorithm`・`z-buffer-algorithm`・`ray-tracing-algorithm`のように揃える。1本ずつ最適なslugを考えさせると、同じ節に並んだときに語尾がばらついて一覧が読みにくくなる。

ここまで済ませると、本文を書く段階ではリンク先が出揃っている。執筆自体は`/author-style-writer <slug>`の担当で、リンクの差し込みもそちらで行う。`prepare-link-targets`には記事の`.svx`を1文字も書き換えさせない。

## 編集指示は本文の中に置く

草稿が出てきたあとは、読み返しながら直したい箇所が出てくる。ここに図版が欲しい、この段落は消したい、デモの初期値が違う、といったもの。これを別のメモに書き出すと、記事を読み返すたびにメモとの突き合わせが要る。

そこで、==編集指示をディレクティブとして本文に直接置く==ことにした。mdsvexの独自ディレクティブなので、開発サーバで記事を開けば帯として表示される。

- `:::Todo`：図版・デモが欲しい箇所。中身にはどんな図かを書く
- `:::Add`：加筆したい箇所。中身は加筆の指示
- `:::Delete`：消す予定の記述。中身は削除対象の本文そのもの
- `:::Fix`：すでにある図版・デモ・文章への修正指示
- `:::Pending`：残すか消すか決めきれていない文章

あわせて、HTMLコメントでのTODOは禁止にした。`<!-- TODO: ... -->{:html}`は本文に表示されないので、書いた本人が見落とす。地の文に`TODO：`と書くのも同じ理由で禁止にしている。ディレクティブなら、記事を読み返した瞬間に目に入る。

見た目はdiffに寄せてある。`:::Add`は緑の帯と行頭の`+`、`:::Delete`は赤の帯と`-`、`:::Fix`は琥珀の帯と`!`（context diffが変更行に使う記号）。`:::Pending`は`:::Delete`と同じ赤い帯にして、ラベルの「(保留中)」だけで区別する。主な用途が「消すかどうかの検討」なので、消すと決まったものと決まっていないものを、あえて同じ見た目に置いた。

{/* TODO: 図版 — 本文中に:::Add / :::Delete / :::Fixの帯が表示されている記事のスクリーンショット */}

`:::Fix`だけは`target`属性を取る。`svg`ならSVG図解、`demo`ならThree.jsデモ、省略時は`text`で文章。=p=この属性が、そのまま担当スキルの振り分けになる。==`svg`は`/svg-diagram-component`、`demo`は`/add-threejs-demo`、`text`は`/author-style-writer`が引き取る。

まだ無いものを作るのが`:::Todo`と`:::Add`、あるものを直すのが`:::Fix`という切り分けにしてある。デモの初期値やUIラベルの直しは後者に入る。

### 溜めた指示をまとめて片付ける

`/apply-edit-requests <記事slug>`は、記事に残っている`:::Add`・`:::Delete`・`:::Fix`を1回でまとめて処理する。

種別・位置・指示・担当・対応方針を並べた表で全ブロックを提示し、承認を取ってから実行に入る。曖昧な指示は解釈を併記して、この表の段階でまとめて確認する。1件ずつ聞き返されると、溜めておいた意味が無い。

処理順は、文章系をファイルの上から順に、次にSVG、最後にデモ。文章を上から追うのは、文体ガイドの読み込みが1回で済むのと、前後の流れを見ながら書けるため。ブロックごとにガイドを読み直させない。

`:::Delete`には注意書きを足した。他の3つと違って**中身が指示ではなく削除対象の記述そのもの**なので、中身を「消し方の指示」と読み違えると、記述を残したままブロックだけ外すことになる。

`:::Todo`と`:::Pending`はこのスキルの対象外にした。`:::Todo`は図版・デモの新規作成で、配置先の相談やデモ案の提案が入るので、`/svg-diagram-component`・`/add-threejs-demo`を個別に呼ぶ。`:::Pending`は中身が候補の本文そのもので、採用するかどうかを決めるのは私だ。読み飛ばさせて、消させない。

## 公開はチェックではなくゲートにする

frontmatterから`draft: true{:yaml}`を外すと記事が公開状態になる。ここで回す作業一式が`/publish-article <slug>`。

このスキルの手順0は、`:::Todo`・`:::Add`・`:::Delete`・`:::Fix`・`:::Pending`が本文に残っていないかの確認になっている。=p=1件でも残っていたら、公開時タスクへは進まない。==`visual`フラグもタスクリストもOGP画像も触らず、そこで止まる。

「残っていたら報告する」というチェック項目の1つにすることもできたが、それでは編集指示の帯が付いたまま公開される事故を防げない。読者に見える形で表示されるものなので、報告ではなく通過条件にした。

止まったときに出るのは、そのままコピペして実行できるコマンドの並び。

```bash title="ゲートで止まったときの案内"
/svg-diagram-component 水晶体分光透過率のグラフ
/add-threejs-demo hidden-surface-removal-methods Zバッファ法の深度比較
/apply-edit-requests hidden-surface-removal-methods
```

`:::Todo`はブロックごとに1行で、中身をそのまま渡す。`svg-diagram-component`はこの文字列でページ内のプレースホルダを検索するので、`TODO：`のような接頭辞を足すと突き合わせが外れる。`:::Add`・`:::Delete`・`:::Fix`は何件あっても`/apply-edit-requests`の1行にまとめる。`:::Pending`だけは案内するコマンドが無いので、行番号と冒頭を挙げて採否を尋ねる形にした。

そして、スキル自身がブロックを消すことは禁止している。対応するのか、指示ごと取り下げるのかは私が決める。

ゲートを通ったあとの公開時タスクは3つ。`$lib/demo/`のコンポーネントを使っているページへの`visual: true{:yaml}`の追加、文体解析タスクリストの`[draft]`注釈の解除、そしてOGP画像の生成。

このうちOGP画像だけは、コミットの後に回している。`visual`フラグとタスクリストは記事の`.svx`と同じコミットに載せたいが、OGP画像の生成物（PNG・JSON・マニフェスト・タスクリスト）は記事本文とは別コミットにするのがこのリポジトリの慣例で、生成そのものも`draft`が外れていないと走らない（draftページはglobや自然言語指定の展開から除外される）。そのため、このスキルには`--before-commit{:bash}`と`--ogp{:bash}`というフェーズ指定がある。コミットを作る`/commit-this`が、コミットを挟んで前半と後半を呼ぶ。

`/commit-this`は、差分から`draft: true{:yaml}`の削除を見つけると`/publish-article`を自動で呼ぶ。公開のコミットを作るだけで公開時タスクが回るので、私が手で叩くのは、ゲートで止まったときの対応と、自動実行しないことにした2つ（文体ガイドの更新とPR説明文の更新）だけになる。

## 数える・書き写す作業はスクリプトに渡す

一覧YAMLの並びは、2つのタスクリストにそのまま写されている。`ogimage/OGP-TASKLIST.md`（OGP画像を生成したか）と`writing-guides/STYLE-ANALYSIS-TASKLIST.md`（文体分析にかけたか）で、どちらも記事ごとに`[x]`・`[ ]`・`[draft]`・`[ページ未作成]`が並ぶ。

同じ並びを3か所に持っているので、YAMLを並べ替えたり、下書きリンクを雛形に変えたりすればずれる。これを照合スクリプトで揃える。

```bash title="一覧YAMLを編集したあと"
node scripts/sync-tasklists.mjs --check   # 差分を報告するだけ（差分があれば exit 1）
node scripts/sync-tasklists.mjs --write   # 差分を書き込む
```

このスクリプトには、触ってよい範囲を狭く決めてある。直すのは並び順・行の過不足・`[ページ未作成]`と`` [draft] `/route` ``の変換まで。**`[x]`は作りも消しもしない。** `draft: true{:yaml}`なのに`[x]`が付いているような矛盾は、警告として出るだけで直らない。生成済み・分析済みの記録は実際にやった作業の記録であって、YAMLから導けるものではないからだ。

もう1つ、YAMLに想定外の記述があるとエラーで停止して、1行も書き込まない。途中まで書いて止まると、タスクリストが半端な状態で残る。それを後から人が見て直すより、何もしていない状態で止まってくれた方がいい。

エージェント側の手順書には「エラーで落ちたらメッセージをそのまま報告し、タスクリストを手で書き換えて取り繕わない」と書いてある。ここを書いておかないと、親切心でタスクリストを直しにいってしまう。

同じ考え方で、`scripts/style-*.mjs`という補助スクリプト群も置いている。文体ガイドのルールIDの採番、根拠ファイルの機械生成、支持記事数の集計、昇格候補の抽出。=p=数える・書き写すという作業をエージェントにさせない。==これらはメインセッションがBashで実行する。

## コミットメッセージを次の分析の材料にする

最後に、コミットメッセージの規約。記事の`.svx`をコミットするときは、次のように書き分けている。

- AIに書かせた初稿：`<title> [ai-draft]`
- 初稿ではないが、AIによる修正しか含まない：`<title>：修正内容 [ai-draft]`
- 人手で調整した：`<title>：調整内容`（`[ai-draft]`は付けない）

この`[ai-draft]`は、文体ガイドを更新する`author-style-analyzer`が読む。AI草稿のコミットと、その次に来る人手修正のコミットの差分が、そのまま「AIの書いたものを私がどう直したか」の記録になる。ここから抽出したものが、推敲ガイド`refine-style.md`になっている。

コミットメッセージは履歴の説明であると同時に、分析器への入力でもある。=p=規約を守らずにコミットすると、その記事は差分の材料にならない。==

例外を1つ置いた。`author-style-writer`の編集モードで私が指示した修正は、書き換えたのがAIでも`[ai-draft]`を付けない。指示の内容自体は私の判断なので、AI草稿の差分として数えられると分析の材料が狂う。この場合は「依頼された修正」の扱いにして、件名に何を直したかを書き、本文にはどんな依頼だったか・なぜそう変えたかを残す。後から履歴を見て判断理由を辿れるようにするためだ。

工程を割ってみると、スキルの数が増えた。READMEのスキル一覧はもう一目で見渡せる長さではないし、`publish-article`のように「手順の正典はこのスキル」と断ってREADMEと二重管理になっている箇所もある。工程を分けたぶん、工程どうしの繋ぎ目を説明する記述が増えている。

`:::Pending`の運用もまだ手探りで、採否を決めないまま溜まっていく。公開のゲートで引っかかって初めて向き合うことになるので、そこで慌てて決めることも多い。決めきれないものを本文に置いておける仕組みが欲しくて作ったのに、決める機会を公開直前まで先送りしているだけになっている。

`apply-edit-requests`が1回1記事なのも、そのうち変えたい。読み返しは複数の記事をまたいで行うので、指示は複数の記事に散らばって溜まる。まとめて片付けたいが、同じセッションで複数の`.svx`を書き換えると文章の一貫性が怪しくなるので、今は1記事ずつに縛っている。
