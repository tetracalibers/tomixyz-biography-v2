[Color Prism](/projects/color-prism)のコンテンツ制作は、適宜人間の判断を挟むために、タスクごとに複数のスキルに分けて進めている。
[CGページ](https://color-prism.net/cg/)を例にすると、1つの記事を公開するまでのタスクの流れは、大まかに次のような感じ。

1. ページの雛形ファイルの作成（`/create-cg-page{:bash}`スキル）
2. 記事に含めたいトピック・キーワードの洗い出し（人間）
3. 関連リンク先ページの作成（`/prepare-link-targets{:bash}`スキル）
4. 草稿の執筆（`/author-style-writer{:bash}`スキル）
5. 構成やデモの配置を確定（人間）
6. 図版やデモの実装と埋め込み（`/add-threejs-demo{:bash}`スキル）
7. 文章の調整・編集指示の追加（人間）
8. 編集指示に基づく一括修正（`/apply-edit-requests{:bash}`スキル）
9. 納得のいく仕上がりになるまで調整（人間）
10. 公開時タスクの実行（`/publish-article{:bash}`スキル）

どのスキルも、自分の担当が終わったら、次に叩くべきスキルとその引数を案内して止まるようになっている。

## 準備：雛形ページの作成とページ一覧の更新

ページ用の空ルートファイルの作成ですら、スキルを経由して行う。それには、記事一覧データとの整合性を担保する目的もある。

未作成ページも含めたページ一覧のデータはYAMLファイルで管理していて、記事一覧ページはこのYAMLデータをもとに生成されるようになっている。

<FigureBox src={img_CgTransformationPage} />

```yaml showLineNumbers {7,17-18}
title: 変換と投影
summary: 座標変換・投影・画像の幾何学的変換
sections:
  - heading: 図形の幾何学的変換
    id: coordinate-transform
    links:
      - slug: coordinate-systems
      - slug: basic-transformations
      - slug: transformation-composition
      - slug: reflection-and-skew
      - slug: affine-transformation
      - slug: projective-transformation
  - heading: ビューイングパイプライン
    id: viewing-pipeline
    links:
      - slug: viewing-pipeline-transformations
      - title: 階層モデリング # CG 2-4-4
        group: ["CG"]
```

7行目のような`slug{:yaml}`が決まっているものは作成済みページで、17~18行目のように`title{:yaml}`しか決めていないものはルートファイルすら存在しない未作成ページ。

ルートファイルを作成するときは、`/create-cg-page{:bash}`スキルを使う。このスキルはSvelteKitのルーティング規約に沿ったページ用の雛形ファイルの作成、YAMLファイルの書き換えを行い、`routes`ディレクトリの構造とYAMLデータの整合性を保つ。タイトルからslugを考えるのもスキルの仕事。

```bash
/create-cg-page 階層モデリング
```

### まずは関連リンク先を用意

わからない関連用語を気軽に学びに行けるのは、ハイパーリンクを備えるWebならではの体験だと思っている。Webならリンクをワンクリック、しかし本では巻末にある「参考文献」リストを参照し、図書館に行って探さなければならないのだ。

なので、本文に出てくる語のうち、他ページで詳しく取り上げているものは積極的にリンクにしたい。
ただ、リンク先の関連ページがまだできていない場合に「そっちのページができてからリンクを設定しよう」なんて後回しにしていると、絶対に忘れる。リンクし忘れた語は本文に埋もれて、後から拾い直すのは大変なのだ。

そのため、関連ページ側の本文がまだ書けていなかったとしても、近日中に書くつもり…と心の中で弁解して、リンクは設定してしまう方式にしている。

そこで執筆の前に実行するのが、`/prepare-link-targets{:bash}`というスキル。

```bash
/prepare-link-targets photorealism-and-reality-elements 三面図,工業製図,線画,...
```

このスキルは、引数で与えられたキーワードを主題として扱う記事が他に存在しないかを判断する。
主題として取り上げる記事が他に存在すれば、そのページをリンク先として設定するために、必要に応じて`/create-cg-page{:bash}`スキルでページを作成する。

### 草稿の自動執筆

関連リンク先が出揃ったら、`/author-style-writer{:bash}`スキルで草稿の執筆を行う。

```bash
/author-style-writer photorealism-and-reality-elements 三面図,工業製図,線画,...
```

第一引数には書きたい記事のslug、第二引数には記事に含めたいキーワードを渡す。スキルは、キーワード群をもとにこの記事の主題を把握し、解説の流れやセクションの構成を設計し、すべてのキーワードを適切な重要度で含めながら、記事本文を執筆する。

## 編集：編集指示の見える化と一括修正スキル

生成された草稿を人手で微調整していくが、AIに修正を依頼したい箇所も出てくる。

- 複数箇所に同じ書式修正を適用したい場合
- 私自身に理解不足があり、AIに加筆してもらった上で精査したい場合
- 曖昧な表現の意図を確認したい場合
- 文章ではなく、デモに対する修正
- etc.

このような修正点を一時的に記事に書き入れるにあたって、これまでは、万が一消し忘れたまま公開してしまうことを避けるため、ページには表示されないコメントとして書き入れていたかもしれない。

しかし今は、人間が最終確認を行っていた頃とは違い、要修正箇所やメモ書きの残存は、AIを使った仕組みを組み込むことで自動的に・確実にチェックすることができる。

そこで、執筆中の段階では、修正点メモも堂々とページに表示されるようにしている。エディタでしか表示されない修正メモコメントと、ブラウザに表示される本文を行ったり来たりする必要もなく、人間としても残タスクがわかりやすくて快適。

### 役割を分けた編集指示ディレクティブ

修正点メモは、のちにそのままAIへの編集指示とすることができる。
そのため、修正内容の種別はAIがわかるようにしておきたく、mdsvexの独自ディレクティブを複数種類用意して、編集指示を種別に合ったディレクティブで囲む方式にしている。

<FigureBox src={img_EditDirectiveExample} caption="背景付きのブロックは編集指示"/>

```md showLineNumbers {4-6,10-12,18-20}
面が隙間なく閉じた不透明な物体では、裏を向いた面は必ず手前側の面に隠れます。
視点からは見えない、物体の裏面はそもそも表示されないため、わざわざレンダリングする必要はありません。このような不可視となる裏面（back face）をあらかじめ除外する処理が:Anki[バックフェースカリング]です。

:::Pending
[隠面消去](/cg/rendering/photorealism-and-reality-elements/)では、重なり合う面のどちらが手前にあるかを確かめて、隠れる面を落としていきます。稜線を対象にする陰線消去も同じで、扱う面や線が増えるほど、この判定は重くなります。
:::

## :WithGroupTag[裏面の判別]{group="{['CG']}"}

インライン数式の前後には空白を空ける
:::

面が裏を向いているかどうかは、面に:Anki[垂直]な向きと、その面から:Anki[視点]を見た向きを比べればわかります。

面に垂直で表側を向くベクトルが、その面の:Anki[法線]です。この:Anki[法線ベクトル]を$$\vec{n}$$、面から視点へ向かう:Anki[視点方向ベクトル]を$$\vec{e}$$とします。

:::Add
:Anki[法線]とは何かについてNote形式で補足
:::

面が視点側を向いているなら、$$\vec{n}$$と$$\vec{e}$$は同じ側を指すため、なす角は:Anki[鋭角]（直角より小さい角）になります。逆に、裏を向いた面では、なす角が:Anki[鈍角]（直角より大きい角）になります。
```

- `:::Todo`：図版・デモが欲しい箇所。中身にはどんな図かを書く

#### 溜めた指示をまとめて片付ける

`/apply-edit-requests <記事slug>`は、記事に残っている`:::Add`・`:::Delete`・`:::Fix`を1回でまとめて処理する。

`:::Fix`だけは`target`属性を取り、`svg`ならSVG図解、`demo`ならThree.jsデモ、省略時は`text`で文章。この属性が、そのまま担当スキルの振り分けになる。`svg`は`/svg-diagram-component`、`demo`は`/add-threejs-demo`、`text`は`/author-style-writer`が引き取る。

`:::Todo`と`:::Pending`はこのスキルの対象外にした。`:::Todo`は図版・デモの新規作成で、配置先の相談やデモ案の提案が入るので、`/svg-diagram-component`・`/add-threejs-demo`を個別に呼ぶ。`:::Pending`は中身が候補の本文そのもので、採用するかどうかを決めるのは私だ。読み飛ばさせて、消させない。

#### 公開はチェックではなくゲートにする

frontmatterから`draft: true{:yaml}`を外すと記事が公開状態になる。ここで回す作業一式が`/publish-article <slug>`。

このスキルの手順0は、編集指示ディレクティブが本文に残っていないかの確認になっている。=p=1件でも残っていたら、公開時タスクへは進まない。==`visual`フラグもタスクリストもOGP画像も触らず、そこで止まる。

「残っていたら報告する」というチェック項目の1つにすることもできたが、それでは編集指示の帯が付いたまま公開される事故を防げない。読者に見える形で表示されるものなので、報告ではなく通過条件にした。

止まったときに出るのは、そのままコピペして実行できるコマンドの並び。

```bash title="ゲートで止まったときの案内"
/svg-diagram-component 水晶体分光透過率のグラフ
/add-threejs-demo hidden-surface-removal-methods Zバッファ法の深度比較
/apply-edit-requests hidden-surface-removal-methods
```

スキル自身がブロックを消すことは禁止している。対応するのか、指示ごと取り下げるのかは私が決める。

ゲートを通ったあとの公開時タスクは3つ。`$lib/demo/`のコンポーネントを使っているページへの`visual: true{:yaml}`の追加、文体解析タスクリストの`[draft]`注釈の解除、そしてOGP画像の生成。

このうちOGP画像だけは、コミットの後に回している。`visual`フラグとタスクリストは記事の`.svx`と同じコミットに載せたいが、OGP画像の生成物（PNG・JSON・マニフェスト・タスクリスト）は記事本文とは別コミットにするのがこのリポジトリの慣例で、生成そのものも`draft`が外れていないと走らない（draftページはglobや自然言語指定の展開から除外される）。そのため、このスキルには`--before-commit{:bash}`と`--ogp{:bash}`というフェーズ指定がある。コミットを作る`/commit-this`が、コミットを挟んで前半と後半を呼ぶ。

`/commit-this`は、差分から`draft: true{:yaml}`の削除を見つけると`/publish-article`を自動で呼ぶ。公開のコミットを作るだけで公開時タスクが回るので、私が手で叩くのは、ゲートで止まったときの対応と、自動実行しないことにした2つ（文体ガイドの更新とPR説明文の更新）だけになる。

#### 数える・書き写す作業はスクリプトに渡す

一覧YAMLの並びは、2つのタスクリストにそのまま写されている。`ogimage/OGP-TASKLIST.md`（OGP画像を生成したか）と`writing-guides/STYLE-ANALYSIS-TASKLIST.md`（文体分析にかけたか）で、どちらも記事ごとに`[x]`・`[ ]`・`[draft]`・`[ページ未作成]`が並ぶ。

同じ並びを3か所に持っているので、YAMLを並べ替えたり、下書きリンクを雛形に変えたりすればずれる。これを照合スクリプトで揃える。

```bash title="一覧YAMLを編集したあと"
node scripts/sync-tasklists.mjs --check   # 差分を報告するだけ（差分があれば exit 1）
node scripts/sync-tasklists.mjs --write   # 差分を書き込む
```

このスクリプトには、触ってよい範囲を狭く決めてある。直すのは並び順・行の過不足・`[ページ未作成]`と`` [draft] `/route` ``の変換まで。**`[x]`は作りも消しもしない。** `draft: true{:yaml}`なのに`[x]`が付いているような矛盾は、警告として出るだけで直らない。生成済み・分析済みの記録は実際にやった作業の記録であって、YAMLから導けるものではないからだ。

もう1つ、YAMLに想定外の記述があるとエラーで停止して、1行も書き込まない。途中まで書いて止まると、タスクリストが半端な状態で残る。それを後から人が見て直すより、何もしていない状態で止まってくれた方がいい。

エージェント側の手順書には「エラーで落ちたらメッセージをそのまま報告し、タスクリストを手で書き換えて取り繕わない」と書いてある。ここを書いておかないと、親切心でタスクリストを直しにいってしまう。

同じ考え方で、`scripts/style-*.mjs`という補助スクリプト群も置いている。文体ガイドのルールIDの採番、根拠ファイルの機械生成、支持記事数の集計、昇格候補の抽出。=p=数える・書き写すという作業をエージェントにさせない。==これらはメインセッションがBashで実行する。

#### コミットメッセージを次の分析の材料にする

最後に、コミットメッセージの規約。記事の`.svx`をコミットするときは、次のように書き分けている。

- AIに書かせた初稿：`<title> [ai-draft]`
- 初稿ではないが、AIによる修正しか含まない：`<title>：修正内容 [ai-draft]`
- 人手で調整した：`<title>：調整内容`（`[ai-draft]`は付けない）

この`[ai-draft]`は、文体ガイドを更新する`author-style-analyzer`が読む。AI草稿のコミットと、その次に来る人手修正のコミットの差分が、そのまま「AIの書いたものを私がどう直したか」の記録になる。ここから抽出したものが、推敲ガイド`refine-style.md`になっている。

コミットメッセージは履歴の説明であると同時に、分析器への入力でもある。=p=規約を守らずにコミットすると、その記事は差分の材料にならない。==

例外を1つ置いた。`author-style-writer`の編集モードで私が指示した修正は、書き換えたのがAIでも`[ai-draft]`を付けない。指示の内容自体は私の判断なので、AI草稿の差分として数えられると分析の材料が狂う。この場合は「依頼された修正」の扱いにして、件名に何を直したかを書き、本文にはどんな依頼だったか・なぜそう変えたかを残す。後から履歴を見て判断理由を辿れるようにするためだ。
