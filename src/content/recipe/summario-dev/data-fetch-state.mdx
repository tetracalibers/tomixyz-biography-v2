[React Router v7](https://reactrouter.com/)では、サーバー側のデータに関する状態管理をフレームワーク側が担ってくれる仕組みが搭載されています。
その仕組みにうまく乗せることで、APIフェッチを行うための`useEffect{:.fn}`や、取得したデータやエラー状態などを保持するための`useState{:.fn}`が不要になります。

充実したReactのエコシステム（UIライブラリ等）を活用しながらも、React特有のつらいポイントを避けることができるのは大きなアドバンテージだと感じ、Summarioの開発では[Next.js](https://nextjs.org/)ではなくReact Router v7を選びました。

しかし、1つのページに多数の機能を備えるアプリケーションでは、React Router v7の仕組みにうまく乗せきれない部分も多く、結局データフェッチとその状態管理を[Tanstack Query](https://tanstack.com/query/latest)で補強する方針をとっています。

今回は、React Router v7による実装で悩ましかったポイントを中心に取り上げる形になることをご了承ください。
もちろんReact Router v7の便利さを実感したことも多くあるので、React Router v7の機能でうまく実装できた部分についても、別の回で取り上げたいと考えています。

## React Router v7で脱`useState`/`useEffect`できるか？

React Router v7のアプローチを知るには、Address Bookという公式のチュートリアルを一読するのがおすすめです。

- [Address Book](https://reactrouter.com/tutorials/address-book)

このチュートリアルで登場する次の言葉が印象的で、React Router v7が単にReactの機能に依存するフレームワークではないことが窺えます。

> 🧐 Wait a sec ... How did the sidebar update? Where did we call the `action` function? Where's the code to re-fetch the data? Where are `useState`, `onSubmit` and `useEffect`?!

実際、このチュートリアルでは`useEffect{:.fn}`や`useState{:.fn}`はほとんど使われていません。
巷のブログでも、React Router v7の仕組みをうまく使えば、タブUIやモーダルUIでさえ`useState{:.fn}`を使わずに実装できると評されています。

- [React Router v7で実現するuseStateゼロ開発](https://zenn.dev/dorarep/articles/1dedd5c1b9ee82)

しかし、このような`useState{:.fn}`になるべく頼らない実装を叶える前提として、｢URLに状態を載せること」が求められてきます。
1つの機能を持つページに対し1つのURLを対応づけることが理想形であり、それができない場合のベストプラクティスについてはまだ情報が少ないと感じています。

### ルートモジュールが持つ機能

React Router v7の[Frameworkモード](https://react-router-docs-ja.techtalk.jp/start/modes#framework)では、ページを表すコンポーネントとページのURLを`app/routes.ts`という設定ファイルで対応づけます。

- [Routing](https://reactrouter.com/start/framework/routing)

```ts title="app/routes.ts" showLineNumbers
import { type RouteConfig, route } from "@react-router/dev/routes"

export default [route("list", "./list.tsx")] satisfies RouteConfig
```

この`app/routes.ts`に登録したページを表すコンポーネント（上の例では`./list.tsx`）を、React Router v7では**ルートモジュール**と呼びます。

- [Route Module](https://reactrouter.com/start/framework/route-module)

そして、ルートモジュールに限り、`loader{:.fn}`と`action{:.fn}`という関数が特別な意味を持ちます。

```tsx title="app/list.tsx" showLineNumbers /loaderData/
import { Form } from "react-router"
import { TodoList } from "~/components/TodoList"

// actionはサーバーで実行されるのでDBに直接アクセスできる
export async function action({ request }) {
  const data = await request.formData()
  const todo = await fakeDb.addItem({
    title: data.get("title")
  })
  return { ok: true }
}

// loaderはサーバーで実行されるのでDBに直接アクセスできる
export async function loader() {
  const items = await fakeDb.getItems()
  return { items }
}

export default function Items({ loaderData }) {
  return (
    <div>
      <TodoList items={loaderData.items} />
      <Form method="post" navigate={false} action="/list">
        <input type="text" name="title" />
        <button type="submit">Todoを作成</button>
      </Form>
    </div>
  )
}
```

`loader{:.fn}`はデータの取得、`action{:.fn}`はデータの更新を担い、これらの結果（戻り値）はルートモジュールで`loaderData` / `actionData`という`Props`として受け取れるようになっています。

- [Data Loading](https://reactrouter.com/start/framework/data-loading)
- [Actions](https://reactrouter.com/start/framework/actions)

また、`loader{:.fn}`は初期ロードを担うだけでなく、`action{:.fn}`の完了後にもロードされる（データの自動再検証が行われる）ため、コンポーネントでの`loaderData`を使った表示も自動的に更新されます。

> データの変更は、ルートアクションを通じて行われます。アクションが完了すると、ページ上のすべてのローダーデータが再検証され、UIを最新の状態に保つためにコードを書く必要はありません。

このように、React Router v7では、サーバー側のデータとクライアントの状態の同期をフレームワークが行い、まるでサーバー側の状態にクライアントから直接アクセスできるような書き味を持ちます。

おかげで、クライアント側で明示的に管理しなければならなかった多くの状態をコードから排除することができるわけです。
具体的にどのような状態管理から解放されるのかは、次のドキュメントにまとめられています。

- [State Management](https://reactrouter.com/explanation/state-management)

### `loader`と`action`の肥大化

このようなルートモジュールの仕組みはとても便利なものですが、ページ内に多数の機能を盛り込んだアプリケーションを開発する際には、厳しい制約にもなりうると感じています。

Reactコンポーネントとしてのルートモジュールは各ページに対応するため、基本的には1つのページに`loader{:.fn}`や`action{:.fn}`は1つずつしか置けないことになります。
すると、ページで必要なすべてのデータを1つの`loader{:.fn}`でロードすることになり、さらにページ内の複数箇所で異なるデータ更新処理が必要な場合は、「どの箇所で呼び出されたか？」によって`action{:.fn}`内で処理を分岐しなければなりません。

この単一`loader{:.fn}` / `action{:.fn}`の肥大化を避けるアプローチが存在しないわけではなく、Nested Routesという仕組みを用いることで、1つのページを複数のルートモジュールの入れ子として表現できます。

- [Nested Routes](https://reactrouter.com/start/framework/routing#nested-routes)
- [Layout Routes](https://reactrouter.com/start/framework/routing#layout-routes)

たとえば、全ページ共通のUIとなるサイドバーと、ページによって内容が異なるメインエリアを別のルートモジュールとして分離すれば、それぞれに`loader{:.fn}`や`action{:.fn}`を置くことが可能です。

```ts title="app/routes.ts" showLineNumbers
import type { RouteConfig } from "@react-router/dev/routes"
import { layout, route } from "@react-router/dev/routes"

export default [
  // 親ルート
  layout("layouts/sidebar.tsx", [
    // 子ルート
    route("items/:itemId", "routes/item.tsx")
  ])
] satisfies RouteConfig
```

```tsx title="app/layouts/sidebar.tsx（親ルート）" showLineNumbers
import { Outlet } from "react-router"

export async function loader() {
  const allItems = await fakeDb.getItems()
  return { allItems }
}

export default function SidebarLayout({ loaderData }) {
  const { allItems } = loaderData

  return (
    <>
      <aside className="sidebar-area">{/* allItemsを使った一覧表示 */}</aside>
      <main className="main-area">
        {/* Outletは子ルートをレンダリングする */}
        <Outlet />
      </main>
    </>
  )
}
```

```tsx title="app/routes/item.tsx（子ルート）" showLineNumbers
export async function loader({ params }) {
  const { itemId } = params
  const item = await fakeDb.getItem(itemId)
  return { item }
}

export default function Item({ loaderData }) {
  const { item } = loaderData

  return (
    <>
      {/* Outlet部分に埋め込まれる内容 */}
      <div className="main-area-inner">{/* itemを使った個別詳細表示 */}</div>
    </>
  )
}
```

このようにルートのネストをあまり深くすることなく綺麗に分けられるならよいのですが、どちらにせよメインエリアに機能が集中するようなページでは、メインエリア側の`loader{:.fn}`や`action{:.fn}`が肥大化することは避けられなくなってきます。

さらに、`loaderData`は`action{:.fn}`実行後に自動で更新（再検証）されるため、`loader{:.fn}`でさまざまなデータをまとめて取得している場合、表示の更新（再描画）が広範囲に及んでしまうことも問題となります。

### 初期データから新たなデータに切り替えたい場合

React Router v7では、`action{:.fn}`はデータの更新に専念し、`action{:.fn}`の実行によって自動更新される`loaderData`をもとに表示を行うという形にすることで、データの流れが自然になります。

```
loader -> component -> action -> loader
```

つまり、`action{:.fn}`でデータを返してそれを表示に使うようなことはせず、表示は`loader{:.fn}`からのデータのみに頼るという実装が理想形です。`action{:.fn}`はあくまでもデータ「更新」だけに徹し、データ「取得」は常に`loader{:.fn}`が担うという役割分担を崩さないようにするのです。

---

データの自動再検証によってフレームワーク側が表示を更新してくれる仕組みはとても強力ですが、ユーザーによるボタンクリック操作など、新たなデータを取得するタイミングを指定したい場合もあります。

1. サーバー側のデータ更新後に表示も更新したい場合
2. サーバー側のデータ更新は伴わず、違うデータのリクエストを行って表示を更新したい場合

---

- 1の例：`action`によって新規アイテムを追加し、全アイテムの一覧を更新したい
- この場合は、`loader`が全アイテムを取得する実装になっていれば、`revalidate`によって自動で表示が更新される

---

- 2の例：初回表示では1〜10件目のアイテムを表示し、ユーザーが「次へ」ボタンを押したら11〜20件目のアイテムを表示するように切り替えたい
- この場合は、`loader`に「取得したいデータ範囲」の情報を何らかの形で伝える必要がある
- 推奨されるのは、URLクエリパラメータにその情報を載せること
- もしくは専用の`loader`を用意し、ボタンクリック時に`fetcher.load`で読み込むことで、`action`を新しいデータの取得に使うことは避けられる

- `fetcher`はユーザーインタラクションによって`loader`や`action`を呼び出すための機能
- https://reactrouter.com/how-to/fetchers#loading-data

---

- `loader`で初期データを取得、ボタンが押されたら`fetcher.load`で新たなデータを取得し、表示を切り替える場合を考える

- 初期表示に使うデータは`loader`で受け取りたい（`fetcher`に任せるとクライアントでの`fetch`になるので、初期表示に時間がかかる）
- つまり、初期表示では`loaderData`を、データ取得後には`fetcher.data`を表示したい

- `const data = fetcher.data ?? loaderData`みたいにしてもいいけど…
- `loader`でエラーが起きた場合はレスポンスボディにエラーの詳細を入れて返す場合では、分岐が面倒なことになる

### URLに状態を載せるべきとは限らない

- URLに状態を乗せられるなら、`loader`だけで表示切り替えが済む
- ボタンが押されたら`action`を呼び出すのではなく、URLパスやURLクエリパラメータを変えることで`loader`が呼び出されるようにすればよい
- 実装例：https://reactrouter.com/tutorials/address-book#urlsearchparams-and-get-submissions

- `FolderExprorer`でも同様に`?dir={folderId}`というURLクエリパラメータで表示の切り替えを試みた
- しかし、URLクエリパラメータはキャッシュされない
- 頻繁にクリックされ、「さっきのデータに戻る」ことも多いUIのため、毎回サーバーにリクエストされるのは避けたかった

## Tanstack Queryの導入

### `useQuery`の効用

- 初期データはルートモジュールの`loader`で提供し、`useQuery`の`placeholderData`にセット
- `useQuery`の戻り値`data`は、新たなデータを取得するまでは`placeholderData`になり、データ取得後は新たなデータになる
- JSX側では`data`をそのまま描画すればいい
- 正常取得時の中身とエラー発生時の中身も分けて処理できる

- すでに取得したデータはキャッシュしておける

### `useMutation`との連携

- DBにアクセスして処理を行う`action`を`fetch`で呼び出せる必要が生じた
- つまり、各アクションにURLを割り当てる必要がある
- そこで、APIエンドポイントのように`action`だけをexportするルートモジュールを定義している
